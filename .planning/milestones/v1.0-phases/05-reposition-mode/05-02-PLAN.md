**Main export: generateAmendments(currentVision: ParsedVision, interviewAnswers: InterviewAnswers, affectedSections: VisionSectionId[]): Promise<Amendment[]>**

Orchestration steps (reuse Phase 2/3 machinery):

1. **Load current VISION:** Already provided as parameter (currentVision: ParsedVision)
2. **Pre-fill seed answers:** Call getSectionAnswerSeed() for each affected section (from Wave 1)
3. **Run derive functions:** Call derivePrinciples(), derive12MonthGoal(), etc. from src/found/derive.ts
4. **Fill template:** Call fillVisionTemplate(interviewAnswers) from src/found/template-fill.ts
5. **Quality check:** Call checkVisionQuality(filledVision) from src/found/quality-check.ts
   - If invalid: throw error with missing slots list
   - If valid: proceed to diff
6. **Diff sections:** Compare currentVision vs filledVision for only affectedSections
   - For each affectedSection:
     - Extract oldContent = currentVision[section]
     - Extract newContent = filledVision[section]
     - Create Amendment { section, currentContent: oldContent, proposedContent: newContent, reason: "Repositioning: [section]" }
7. **Return amendments:** Amendment[] in section order

**Error handling:**
- If quality check fails: throw error `Quality check failed: [missing slots]`
- If currentVision missing: throw error `No current VISION found`
- If interviewAnswers empty: throw error `No interview answers provided`
- If affectedSections empty: return []

**Key behaviors:**
- Pure function (does not persist state; caller handles persistence)
- Delegates all heavy lifting to Phase 2 derive/template/quality functions (no duplication)
- Returns only amendments for affected sections (scoped reposition, not full rewrite)
- Each Amendment includes rationale ("Repositioning: [section]") per D-07

**Testing strategy:** 25+ unit tests covering:
- Single affected section (voice) → 1 amendment
- Multiple affected sections (voice + product-direction) → 2 amendments
- All 6 affected sections → 6 amendments (full rewrite like Found mode)
- Amendment diff correctness (before != after for changed sections)
- Quality check failure → throws error
- Missing interviewAnswers → throws error
- Scoped amendments preserve unmodified sections (not included in output)

Reuse Phase 2 derive functions, template-fill, quality-check verbatim.

Create src/reposition/apply.ts with applyRepositionAmendments orchestrator (per D-11, D-12, REPO-04):

**Main export: applyRepositionAmendments(ctx: PluginContext, companyId: string, amendments: Amendment[], approvalRouting: "founder" | "founder+ceo", repositionRunId: string): Promise<ApplyResult>**

Orchestration steps (reuse Phase 3 apply pattern exactly):

1. **Preflight checks:**
   - Validate VISION.md exists in documents
   - Validate amendments list not empty
   - Validate approvalRouting is valid enum
   - Validate companyId valid (company exists)
   - Return error result if any check fails

2. **Sequential write stage (within try/catch):**
   - Load current VISION.md
   - Apply amendments to VISION (section-by-section merge)
   - Write amended VISION to documents via SDK adapter
   - Record visionDocId for rollback
   - Plan cascade using planRepositionCascade()
   - Execute cascade using executeRepositionCascade()
   - Record issueIds, wakeupIds for rollback
   - Return success result

3. **Approval routing:**
   - If approvalRouting === "founder": apply synchronously (step 2 proceeds immediately)
   - If approvalRouting === "founder+ceo": queue to approvals table, return waiting-approval status
     - Reuse Phase 3 approval routing logic (exact pattern)
     - Do NOT write VISION until CEO approves (XC-06 spirit: no auto-edit)

4. **Rollback on failure:**
   - If any write fails: catch error
   - Delete cascade issues (issueIds)
   - Delete VISION document (visionDocId)
   - Return error result with rollback status

**Return structure:**
```typescript
{
  success: boolean,
  visionDocId?: string,
  issueIds?: string[],
  wakeupIds?: string[],
  cascadeResult?: CascadeResult,
  error?: string,
  waitingForApproval?: boolean,
  approvalId?: string,
  rollback?: { issuesDeleted: number, visionReverted: boolean }
}
```

**Error handling:**
- Preflight errors: return early, no writes
- Mid-apply errors: trigger rollback, return error + rollback status
- Approval queue errors: return error waiting-approval (founder must retry)

**Key behaviors:**
- Pure transactionality: either all writes succeed, or all rolled back
- Approval gate enforced: founder+ceo mode never writes until CEO decides
- Idempotency keys on all wakeups (per generateRepositionIdempotencyKey from Wave 1)
- XC-06 safety: no auto-edit of VISION, founder approval gate mandatory

**Testing strategy:** 30+ unit tests covering:
- Preflight failures (no VISION, invalid company, empty amendments) → return early error
- Sequential write success (founder routing) → all writes succeed, return visionDocId + issueIds
- Sequential write with cascade → cascade issues created and linked
- Approval queue (founder+ceo routing) → queue approval, return waitingForApproval, no writes yet
- Rollback on VISION write failure → delete cascade issues, return error + rollback status
- Rollback on cascade failure → delete cascade issues, return error + rollback status
- Idempotency keys → all wakeups use reposition namespace
- Edge cases: empty amendments, missing company, approval rejection

Delegate approval routing logic to Phase 3 (exact copy).

## Trust Boundaries

| Boundary | Description | Risk |
|----------|-------------|------|
| Interview answers → amendment generation | Founder-provided scoped interview answers | Low — template-fill is deterministic string replacement; quality check validates slots non-empty before proceeding |
| Current VISION → diff generation | Existing VISION.md parsed and compared to new | Medium — if parse fails, amendment fails; founder sees error, must retry Found mode to fix VISION |
| Cascade plan → issue creation | Planned cascade issues for affected agents | Medium — if agent screening fails (classifies agent wrongly as newly-provisioned), may create unwanted cascade; mitigated by custom-override warning for each agent |
| Amendment write → VISION.md | Founder-confirmed amendments written to documents | Low — write protected by two-stage approval gate (preview + "I confirm" modal) per XC-06 |
| Founder+CEO approval → apply | CEO agent decision on approval | Low — approval routing deferred to Phase 3; Phase 5 reuses verbatim (no new routing logic) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05 | Tampering | Amendment generation | mitigate | Quality check validates all required slots before filling; invalid amendments rejected (not persisted); founder sees error message |
| T-05-06 | Repudiation | Apply transactionality | mitigate | Rollback creates compensating operations (delete cascade issues, revert VISION); all writes idempotent via idempotency keys; audit trail via amendment changelog |
| T-05-07 | Denial of Service | Cascade planning | mitigate | Agent screening limits affected agents to active (heartbeat recent); newly-provisioned agents filtered out; bounded write count |
| T-05-08 | Information Disclosure | Custom-override detection | mitigate | Warnings shown only to founder; CEO does not see custom instruction details (per Phase 3 pattern); no secrets leaked in amendment diffs |
| T-05-09 | Elevation of Privilege | Approval routing | mitigate | Reuses Phase 3 approval logic (no new elevation paths); founder+ceo mode enforces CEO decision before writes (cannot bypass by founder action alone) |
