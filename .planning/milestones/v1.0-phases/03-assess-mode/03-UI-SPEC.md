## Spacing Scale

**Inherited from Phase 2 (unchanged):**

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, tight text spacing |
| sm | 8px | Compact form element spacing, list gaps |
| md | 16px | Default form field padding, section gaps |
| lg | 24px | Major section padding, modal padding |
| xl | 32px | Layout column gaps, interview panel padding |
| 2xl | 48px | Major section breaks, panel boundaries |
| 3xl | 64px | Full-page top/bottom spacing (sidebar width constraint) |

**Exceptions (Phase 3 specific):**
- Confidence bar height: 8px (fits within `sm` spacing module)
- Evidence chip gap: `gap-xs` (4px between chips)
- Drift item card padding: `p-lg` (24px)
- Diff block padding: `p-md` (16px, inside collapsible details)

**Sidebar width constraint:** ~360px — no horizontal scrolling. Diff renderer must wrap at column width.

## Confidence Bar Styling (Phase 3 Visual)

Drift items display a horizontal confidence bar (8px height) showing strength of detected drift:

- **Red zone** (0.0–0.33): Low confidence — shown to founder but lower prominence. Foreground color: `text-destructive` (red).
- **Yellow zone** (0.33–0.66): Medium confidence — default prominent state. Foreground color: `text-accent` (amber/accent color from host).
- **Green zone** (0.66–1.0): High confidence — maximum prominence. Foreground color: `text-accent` (green accent variant from host, or same accent if host doesn't distinguish).

**If host design tokens lack green/amber/red variants,** render all confidence bars in `text-accent` and differentiate via opacity or border-width instead:
- Low (0.0–0.33): `opacity-50 border border-accent`
- Medium (0.33–0.66): `opacity-75 border border-accent`
- High (0.66–1.0): `opacity-100 border-2 border-accent`

Confidence value displayed inline to the right of bar in `text-label` gray text: "78% confidence".

## Interaction Patterns

### AssessPanel Layout (Main Entry Point)

**Header** (fixed at top, sticky):
1. **Company Name** — left-aligned, `text-display font-bold`
2. **Routing Mode Badge** — centered, `text-label` gray text + accent highlight. Shows "Routing: founder" or "Routing: founder+ceo". Clickable → opens routing-change modal.
3. **Action Buttons** (right-aligned):
   - "Run a drift audit" button (primary) — disabled if no VISION.md; tooltip explains
   - "Discard" text button (secondary, gray) — only appears if audit in progress

**Helper text** (below header, light gray `text-foreground/70`): 
"Audit your company's recent work against your vision document. This helps you stay aligned as you grow."

**Main content area** (scrollable):
- **If no audit in progress:** Empty state with "No drift audit in progress." + "Run a drift audit" button
- **If audit running:** Loading indicator with percentage ("Detecting drift… 42%")
- **If audit complete:** DriftReportPanel (see below)
- **If audit paused/cached:** Resume notification + same DriftReportPanel

**Sticky footer** (fixed at bottom):
- "Apply [N] accepted amendment(s)" button
- Disabled until at least one drift item accepted
- On click: opens preview screen → confirmation modal → Apply orchestrator

---

### DriftReportPanel Structure

**Grouping by VISION section:**
- All drift items grouped under their respective VISION section headers
- Section header format: "{Section name}" with optional severity badge (e.g., "Mission — blocker" or "Voice — warn")
- Sections appear in VISION template order (mission, mandate, voice, principles, etc.)
- Empty sections (no drift) hidden

**Per-drift-item card layout:**
1. **Card header** (padded `p-lg`, light `bg-card` background)
   - Left: Confidence bar (8px height, color-coded by confidence level)
   - Right: "{confidence}% confidence" in `text-label` gray

2. **Card body** (padded `p-lg`, white/background)
   - **Evidence section** (h4 heading in `text-heading font-bold`):
     - List of 3–5 evidence chips (max 5; "See all N" expand if more)
     - Each chip: source icon + source label (Issue #42 / Comment / Document)
     - Chips clickable → navigate to source in Paperclip UI
     - Chip gap: `gap-xs` (4px)
   
   - **Amendment proposal section**:
     - Heading: "Proposed amendment:" in `text-label`
     - Collapsible `<details>` containing unified diff
     - Diff viewer shows 3–5 lines of context (before + after)
     - Syntax: added lines prefixed `+` in accent color, removed lines prefixed `-` in destructive color
     - Example:
       ```
       - voice: "technical and formal"
       + voice: "approachable, expert, friendly"
       ```
   
   - **Accept/Reject buttons** (below amendment):
     - Two buttons side-by-side: "Accept" (left, primary accent style when selected) + "Reject" (right, plain/gray when selected)
     - Not radio buttons — explicit toggle buttons
     - State: Accepted buttons show accent highlight + checkmark; Rejected buttons show gray + X or plain styling
     - Only one state per item (accept OR reject, not both)
     - Default state: neutral (neither selected until founder clicks)

### Approval Routing Mode Change Modal

Triggered by clicking "Routing: [current]" badge or "Change approval routing" button.

**Modal header:** "Approval routing"

**Modal body:**
```
How should amendments be approved?

⭕ Founder only (fast, founder decides unilaterally)
⭕ Founder + CEO agent (collaborative, requires CEO sign-off)

Current: [selected option]
```

**Radio buttons** (not toggle):
- "Founder only — amendments apply immediately after your approval"
- "Founder + CEO agent — amendments queued for CEO review"

**Buttons:**
- "Cancel" (secondary) — closes modal
- "Save routing" (primary) — writes new routing config to Plugin SDK worker-state, closes modal, shows toast confirmation

**Save feedback:** "Approval routing updated to [new mode]." (toast in `text-accent`)

---

### Preview Screen (Amendment Review)

Full-panel scrollable screen (or modal, planner decides). Shows all accepted amendments before final confirmation.

**Header:** "Review amendments before applying"

**Content:**
- List of all accepted amendments grouped by VISION section
- Each amendment shows:
  - Section name (heading, `text-heading font-bold`)
  - Current version (from VISION.md, in light `bg-card`)
  - Proposed version (in `bg-background` with accent border highlight)
  - Evidence summary (e.g., "3 agents deviated from this in the last 30 days")

**Buttons:**
- "Cancel" (secondary) — returns to DriftReportPanel
- "I confirm — apply amendments" (primary, accent) — opens confirmation modal

---

### Confirmation Modal (Two-Stage Gate, Reused from Phase 2)

**Modal header:** "Apply amendments to your vision"

**Modal body:**
```
Apply will:
- Update your VISION.md with [N] amendments
- Create [N] cascading issues for affected agents
- Queue wakeup requests to notify the company

This change is logged in your VISION amendment history.

Write count: 1 document updated, [N] cascading issues, [N] wakeups
```

If `founder+ceo` mode: Note about approval routing:
```
Note: Your CEO agent will review these changes before they apply.
```

**Buttons:**
- "Cancel" (secondary) — returns to preview
- "I confirm — apply amendments" (primary, accent) → runs Apply orchestrator

### Apply Progress UI (from Phase 2, Assess variant)

**Modal or full-panel overlay (blocking interaction):**

Sequential step indicator:
```
Validating setup…
✓ Preflight checks
Amending vision document…
✓ VISION.md updated
Creating cascading issues…
✓ N affected agent issues created
Queuing wakeups…
✓ Wakeup requests queued
```

Each step shows:
- Status: "…" (in-progress) or "✓" (complete)
- Step name

**On success:**
```
✓ Amendments applied!

Your vision document has been updated and [N] agents have been notified.
Check your company's issue list for cascading work items.

[Go to company] button → closes plugin, navigates to company
```

**On failure at any step:**
```
Apply failed: [Step name]

Error: [Readable error message]
Next step: [Recovery instruction]

Rollback:
✓ Cascading issues deleted
✓ Vision document reverted

[Retry] | [Close]
```

**If founder+ceo mode with CEO approval pending:**
```
✓ Amendments submitted for CEO review

Your CEO agent is reviewing the proposed changes.
You'll be notified when a decision is made.

[Done] button → closes Apply flow
```

Then show "Waiting for CEO approval" state in main panel (see below).

### Founder+CEO Approval Waiting State

When amendments queued for CEO in `founder+ceo` mode:

**Panel state (DriftReportPanel replaced with waiting screen):**

Heading: "Waiting for CEO approval" in `text-heading font-bold`

Body text: "Amendments submitted [time ago] for review. Your CEO agent will respond shortly."

Example: "Amendments submitted 2 minutes ago for review."

**Action buttons:**
- "Refresh" button (secondary) — polls `approvals` table for CEO decision. Shows `[refreshing]` state, then updates message if decision arrived.
- "Cancel request" link (text) — retracts the approval request, clears amendments from waiting state, returns to DriftReportPanel (optional in v1; may defer to Phase 4).

**Helper text:** "Your CEO agent is reviewing the proposed changes. You'll be notified when a decision is made." in `text-foreground/70`.

---

### Custom Override Warning (During Apply Preview)

Shown in preview screen when an affected agent has custom instruction overrides (`adapter_config.instructions` deviates from baseline):

**Warning card** (light red/amber background via `border-destructive` or `bg-card` with left border `border-l-4 border-destructive`):

```
⚠️ Agent [Agent name] has custom instructions

This agent's instructions have been customized beyond the preset baseline.
The [section name] amendment will cascade as a new work item, but 
the agent's custom overrides will not be automatically merged.

Review the following before applying:
[Show diff of what would be added vs agent's custom config]

☑️ I've reviewed the override conflict and approve cascading anyway
```

Checkbox-style confirmation required before allowing Apply to proceed.

## Accessibility

- All interactive elements keyboard-navigable (Tab, Enter, Space)
- Form labels linked to inputs via `htmlFor` / `id` (if form-based toggle)
- Confidence bar has `aria-label="Confidence: N%"`
- Error messages linked to relevant controls via `aria-describedby`
- Modal backdrop blocks background interaction (focus trap)
- Evidence chips have `aria-label="Issue #42"` or equivalent for screen readers
- Color-coded zones (confidence red/yellow/green) must have text label fallback (percentage text visible at all times)

## Designer Notes (Claude's Discretion)

This contract locks the **what** (behavior + copy + visual relationships) but leaves **where** for the planner:

1. **Approval routing toggle placement** — header badge (current recommendation) vs settings modal vs inline button? Recommendation: badge + clickable label for quick access (founder may toggle frequently).
2. **Diff collapsible behavior** — all diffs collapsed by default, or expand highest-confidence items? Recommendation: collapsed (reduces initial cognitive load), expand on demand.
3. **Evidence chip max display** — currently 3–5 visible before "See all". Adjust based on sidebar width during planner phase.
4. **Approval waiting polling interval** — currently no tight loop (founder refreshes manually). Could add client-side timer (5–10s) with visual "checking..." indicator. Deferred to planner preference.
5. **Custom override warning placement** — shown in preview screen above Apply button. Could alternate: show in report during review (before preview). Recommendation: preview-time (more actionable context before final gate).

All above locked in **planner** phase per Phase 1 UI-SPEC.md conventions. UI-SPEC provides the contract; planner places components.
