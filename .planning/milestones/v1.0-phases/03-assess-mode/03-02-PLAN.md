**Create `src/assess/cascade.ts`** per D-12, D-13, D-14:

1. **`planCascade(vision: ParsedVision, acceptedAmendments: Amendment[], agents: Agent[]): CascadePlan`**
   - Input: parsed VISION, list of accepted amendments (section name + new content), full company agent roster.
   - For each accepted amendment, determine affected agents based on section:
     - voice/principles → all customer-facing agents (infer from role: "customer-success", "sales", "marketing", "product")
     - revenue-model/launch-plan → "cfo", "operations" 
     - product-direction → "cto", "vp-eng", any with "engineer" in role
     - org-structure/operating-philosophy → all agents
     - Other sections → optional (default: all agents for safety, founder can review)
   - Apply agent screening (D-13): exclude agents where `created_at > now - 7 days AND last_heartbeat_at is null` (newly-provisioned, not yet started).
   - Detect custom overrides (D-14): for each affected agent, check if `agent.adapter_config.instructions` deviates from preset baseline. Store `{ agentId, agentRole, hasCustomOverrides: bool, override_snippet: string }` in cascade plan.
   - Return `CascadePlan` with:
     - `affectedAgents: Agent[]` (filtered, non-newly-provisioned)
     - `customOverrideWarnings: OverrideWarning[]` (agents with custom config)
     - `issuesByAgent: { [agentId]: IssuePlan }` (one issue per affected agent with proposed work)

2. **`executeCascade(adapter: SDKAdapter, cascade: CascadePlan, companyId: string, assessRunId: string): Promise<CascadeResult>`**
   - Sequential loop: for each agent in cascade.affectedAgents:
     - Create issue via adapter: title = `[Cascade from Assess] Review ${amendment.section} changes`, description includes amended section content + evidence summary.
     - Link issue back to assessment via issue body: `compass:assess:cascade:${assessRunId}`.
     - Queue wakeup via adapter using idempotency key: `compass:assess:${companyId}:${assessRunId}:${agent.id}`.
   - Track issued IDs and wakeup IDs in CascadeResult for rollback.
   - If any issue creation fails, halt and return error (caller decides rollback strategy).

**Create `src/assess/apply.ts`** extending the Pattern from Phase 2 `src/found/apply.ts` (D-15, D-09):

1. **`applyAssessmentChanges(adapter: SDKAdapter, company: Company, acceptedAmendments: Amendment[], approvalRouting: 'founder' | 'founder+ceo', assessRunId: string): Promise<ApplyResult>`**
   - Main orchestrator. Reuses Phase 2 D-09 pattern: **preflight → sequential → rollback**.

2. **Preflight stage:**
   - Check: VISION.md exists in documents table
   - Check: Parse VISION.md succeeds
   - Check: No prior in-flight assess run (worker-state check)
   - Check: Amendments contain at least one accepted item
   - If any check fails, throw `PrefailureError` (caller catches and surfaces to UI)

3. **Sequential write stage (if founder routing):**
   - Stage 1: Write amended VISION.md to documents table via `adapter.writeDocument()`.
     - Call `serializeVision(amendedVision)` to rebuild markdown.
     - Idempotency key: `compass:assess:${company_id}:apply:${assessRunId}:vision` (track for rollback)
   - Stage 2: Plan cascade via `planCascade()`, execute via `executeCascade()`.
     - Track created issue IDs + wakeup IDs for rollback.
   - Stage 3: (optional) Update engagement memory in Phase 6; skip in v1 (no MEM impl yet).
   - Return `ApplyResult` with write IDs, summary ("Updated VISION with N amendments, cascaded to N agents").

4. **Sequential write stage (if founder+ceo routing):**
   - Stage 1: Insert approval request into `approvals` table via `adapter.insertApproval()`.
     - Payload: `{ type: 'compass.assess.amendment', companyId, proposedVision: serialized, amendments: [...], assessRunId }`.
     - Idempotency key: `compass:assess:${company_id}:approval:${assessRunId}`.
     - Do NOT write VISION or cascade yet.
   - Return `ApplyResult` with status: `{ waitingForApproval: true, approvalId: string }` (caller's UI shows waiting state).
   - Worker will poll approval table; on CEO decision, execute stages 2–3 above.

5. **Compensating rollback (on any failure during sequential writes):**
   - Reverse order: delete cascade issues → delete VISION amendment → complete.
   - Each rollback step wrapped in try-catch; if rollback itself fails, return explicit error with manual cleanup steps.
   - Per D-15: "Check [link to company] before retrying."

6. **Audit trail:**
   - Log each stage to `assessment_audit: { stage, status, timestamp, error?, rollback_status? }` in worker-state.
   - Persists for founder inspection + replay logic (Phase 6).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Amendment acceptance | Founder reviews + accepts per-item; cascade respects only accepted items |
| Approval routing | Per-company config determines if CEO review required; cannot be bypassed |
| Cascade targeting | Agent role-based selection; custom overrides surfaced for explicit founder confirmation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Spoofing | Amendment source attribution | Mitigate | Amendments include evidence list (issue IDs, timestamps) from SDK; amendment author implicit (founder). Changelog entry will include founderIdentity in Phase 6. |
| T-03-07 | Tampering | Transactional integrity | Mitigate | Preflight validates VISION parse succeeds. Sequential writes tracked with idempotency keys. Rollback reverses each write in reverse order. On rollback failure, explicit manual cleanup steps returned to founder. |
| T-03-08 | Repudiation | Cascade audit | Mitigate | Each cascade issue includes assessment run ID in body. Wakeup idempotency key encodes assessRunId. Audit trail in worker-state logs each stage. Cannot edit after apply. |
| T-03-09 | Information Disclosure | Custom override detection | Mitigate | Custom override warnings shown to founder in UI preview (before apply). Founder must explicitly confirm per-agent. Diffs not exposed to other parties (UI-only). |
| T-03-10 | Denial of Service | Cascade perf | Accept | Cascade loop O(n) on affected agents (max ~20 per company). Issue + wakeup creation via SDK (SDK bounds requests). Will timeout with alert if >100 agents affected (not enforced in v1, acceptable per PROJECT.md). |

</threat_model>
