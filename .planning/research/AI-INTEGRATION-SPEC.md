## 1. System Classification

**System Type:** Hybrid — UI Orchestrator + Strategic Interview Driver. Not RAG, not autonomous agent, not pure conversational. Compass invokes per-company host-managed agents via Paperclip SDK and renders/persists their outputs with local amendment + cascade logic.

**Description:**
Compass is a Paperclip plugin that consults founders across the company lifecycle (Found, Assess, Revive, Reposition). Each mode invokes one or more host-managed agents (CEO, Product, Engineer, etc., already provisioned per-company by Paperclip) with a structured prompt, streams responses to the plugin sidebar, validates output with Zod, and persists results to `documents` + `ctx.state`. "Good" = strategic guidance founders trust, captured in artifacts (VISION.md amendments, drift reports, pivot plans) that shape the AI company's direction.

**Critical Failure Modes:**
1. **Wrong-agent invocation** — calling the wrong host agent for the mode (e.g., invoking Engineer for vision interview) → off-topic strategic guidance, founder loses trust.
2. **Schema-violating output** — agent returns text that doesn't match the expected Zod schema (e.g., amendment without `path`/`rationale`) → silent dropout or runtime crash applying changes.
3. **Stream loss / partial response** — `sendMessage` event stream drops mid-interview → orphan state, founder sees half a question, no resume.
4. **Cross-company leakage** — reading or writing wrong `companyId` → strategic data exposed across tenants (multi-tenant OSS plugin = blast radius is high).
5. **Idempotency violation on wakeups** — duplicate `agents.invoke` for same intent → duplicate amendments, duplicate issues, founder sees same drift report twice.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Startup Advisory & Strategic Consulting — Specifically: AI-augmented company lifecycle management (founding, auditing, revival, repositioning).

**User Population:** Solo and small-team technical founders running AI-staffed companies on Paperclip. They have delegated day-to-day execution to host-managed AI agents and seek periodic strategic check-ins. Users are non-experts in advisory (no YC/startup consultant background) but have deep operational knowledge of their own companies. They expect tool recommendations to be "hard-coded" and deterministic (not vague strategic philosophy).

**Stakes Level:** High — Compass output directly shapes company direction. Amendments to VISION.md cascade to agent behavior; drift misdiagnosis delays course correction; stall misclassification prolongs burnout; pivot recommendations can consume weeks of execution time.

**Output Consequence:** Compass recommendations become:
- Amendments to VISION.md (the company constitution) — live immediately or after founder approval
- New issues queued for host-managed AI agents to execute (e.g., "Implement new go-to-market strategy")
- Scheduled wakeups and strategic check-ins in the Paperclip routine system
- Changes to agent assignments or role definitions
These ARE operational actions on the running company, not advisory-only text.

### What Domain Experts Evaluate Against

**Dimension 1: Mission-Activity Alignment Clarity**

| Aspect | Details |
|--------|---------|
| **Good (advisor accepts)** | Compass names the exact mismatch (e.g., "VISION says build B2B SaaS for SMBs; last 30 days spent 70% on open-source library nobody asked for"). Includes specific dates, PR/issue titles, and dollar impact (e.g., "estimated 2 weeks of engineering time on out-of-scope work"). |
| **Bad (advisor flags)** | Compass says "slight drift detected" without naming it. Or flags drift that contradicts founder's intent ("you said sell to enterprise but tried SMB"—when founder explicitly planned SMB market-test first). Or uses vague language ("suboptimal resource allocation"). |
| **Stakes** | Critical |
| **Source** | YC partner decision frameworks emphasize rapid learning + user feedback cycles. Strategic advisors assess whether teams are executing against stated thesis, not drifting silently. CB Insights: 43% of startup failures stem from poor product-market fit, often because founders didn't align execution to vision. |

---

**Dimension 2: Actionability of Amendments**

| Aspect | Details |
|--------|---------|
| **Good (advisor accepts)** | Amendment specifies: (a) the exact section path in VISION.md (e.g., "mission statement, line 2"), (b) the change rationale with supporting evidence ("last 5 releases prioritized API stability; 3x fewer feature requests for new connectors → simplify to 'build stable API integrations'"), (c) whether founder or founder+CEO should approve. Rationale is falsifiable (if new activity contradicts it, easy to re-amend). |
| **Bad (advisor flags)** | Amendment says "consider reframing your go-to-market" without saying how. Or proposes change so major it requires full vision re-interview ("pivot to AI agents" vs "shift GTM from self-serve to sales-assisted"). Or buries the change in prose instead of structured JSON. Or recommends pivot that ignores sunk cost / team capability (e.g., "switch from SDK to full-stack SaaS" when team is purely infrastructure people). |
| **Stakes** | Critical |
| **Source** | Strategic consulting evaluation (Demand Metric, Prepmatter): Clients assess proposals on "ease of implementation" and "internal consistency." Actionable amendments prevent founder decision paralysis and ensure agent follow-through. |

**Dimension 3: Founder Burnout / Stall Diagnosis Accuracy**

| Aspect | Details |
|--------|---------|
| **Good (advisor accepts)** | Compass narrows stall cause to one of: decision-fatigue loop (too many unresolved blockers), agent underperformance (heartbeat dropped / no-op runs), founder absence/burnout (no founder PRs/comments in 2+ weeks), misalignment between agents (conflicting PRs / unresolved code reviews), scope creep (initial 30-day goal now 6-month task). Includes evidence: specific issue numbers, heartbeat timestamps, founder activity data. |
| **Bad (advisor flags)** | Compass diagnoses "stall" but doesn't say why (vague "momentum lost"). Or attributes stall to "bad market" without checking if agents are actually shipping. Or recommends "pivot" as solution to a decision-fatigue stall (more scope won't help). Or ignores founder burnout signals (53% of founders report burnout per 2024 data; Compass should catch emotional flattening + cognitive clutter). |
| **Stakes** | High |
| **Source** | Founder burnout research (Mercury, Zen Founder, M Accelerator 2025) shows three structural drivers: decision fatigue, identity fusion, recovery deficit. Early alarms: emotional flattening + cognitive clutter. Stalled startups often hide burnout. Strategic advisors must catch both. |

---

**Dimension 4: Avoiding Premature / Reverse Pivots**

| Aspect | Details |
|--------|---------|
| **Good (advisor accepts)** | If Compass recommends pivot, it explicitly names: (a) what was working (with metrics: ARR, retention, feature usage), (b) why it's no longer sufficient (market saturated, unit economics broken, founder no longer motivated), (c) what core capability transfers (e.g., "your API library work is a bigger GTM lever than the SaaS wrapper"). Only recommends pivot if >2 of these are true. Includes "no-pivot" option if reframing mission is safer. |
| **Bad (advisor flags)** | Compass recommends pivot because agents haven't shipped in 3 weeks (that's a stall diagnosis problem, not a strategy problem). Or recommends pivot without checking if founder has enough cash runway. Or pivots to idea that contradicts founder's stated interests ("you hate sales, let's build an enterprise software company"). Or flagged "drift" in one iteration, then "suggests pivot" in the next—founder loses trust in consistency. |
| **Stakes** | High |
| **Source** | YC partners (2025/2026) report that pivots during "some traction" are rare wins (Firecrawl case: pivoted with significant ARR, found bigger market). But premature pivots are costly (sunk engineering time, confused agents). Advisors must validate sufficient evidence before recommending. |

---

**Dimension 5: Cascade Plan Feasibility**

| Aspect | Details |
|--------|---------|
| **Good (advisor accepts)** | Compass generates cascade plan that lists: (1) which issues to create and in what order, (2) which agents can execute each issue, (3) estimated 2-week throughput (e.g., "Product agent can do 1 design + 1 GTM issue in 2 weeks"), (4) risk/blocker that might derail the plan, (5) fallback if an agent times out or produces bad output. Plan is testable (founder can sample one issue, see if agent executes as predicted). |
| **Bad (advisor flags)** | Cascade plan is a prose paragraph ("pursue the following strategic opportunities"). Or lists 10 issues without prioritization. Or requires all agents to coordinate without naming blocking/unblocking dependencies. Or assumes agents won't need founder input (they will—cascade is interactive). Or doesn't name fallback if agent gets stuck. |
| **Stakes** | High |
| **Source** | Startup execution frameworks (Y Combinator, First Round): Strategy is only as good as implementation plan. Cascades must account for agent limitations (no inference, latency, interdependencies). |

### Known Failure Modes in This Domain

**1. Drift Hallucination — Flagging Mismatch That Matches Founder's Actual Intent**

Compass audits VISION.md vs 30-day activity, finds "50% of time on SDK integrations but VISION says 'focus on product.'" Founder dismisses it: "I intentionally shifted focus to SDK because enterprise customers asked for it—this is validation, not drift." Compass loses trust permanently. Root cause: Compass didn't account for founder-driven pivots mid-sprint (vs. goal-less activity). Mitigation: Require founder context before flagging drift; surface "intentional shift" detection (activity spike correlated with new GitHub issue/blog post from founder).

**2. Stall Attributed to Wrong Cause, Leading to Wrong Action**

Company shows 3-week no-op on issues. Compass diagnoses "agent underperformance" and recommends agent swap. Real cause: VISION.md is 6 months old and founders disagree on next direction—agents are blocked waiting for decision. Agent swap doesn't help; founder needs re-interview. Mitigation: Stall classifier must check "is VISION stale?" before diagnosing agent failure.

**3. Cascade Plan Assumes Agent Autonomy Agent Can't Actually Provide**

Cascade says "Product agent will design new GTM flow, create design doc, and present to team." Product agent creates design doc but can't coordinate cross-team feedback or iterate based on dissent. Founder hand-does the coordination work, defeating the purpose of "founders delegate to agents." Mitigation: Cascade must name every place founder input is needed; make it explicit ("Product agent designs, founder reviews and approves before Engineer starts").

**4. Premature Pivot Recommendation When Root Cause Was Burnout**

Founder is exhausted (emotional flattening, 2-week absence from Slack). Compass sees no-op activity for 30 days and recommends pivoting to a "smaller, faster market." Founder burns out more because pivot adds complexity. Real issue: founder needed a 2-week break and clearer decision-making role. Mitigation: Compass checks founder activity metadata (commits, comments, PRs) before attributing stall to market/strategy vs. leadership fatigue.

**5. Approval Gate Escalation to CEO Who Disagrees with Founder**

Compass proposes amendment, routed to founder+CEO for approval. CEO agent disagrees with amendment logic and rejects it. Founder intended amendment but now founder vs. CEO are misaligned in Paperclip. Mitigation: Approval routing must default to founder-only for v1; CEO co-approval is opt-in per-company, not default.

## 2. Framework Decision

**Selected Framework:** None (Paperclip Plugin SDK native)

**Version:** `@paperclipai/plugin-sdk` ^1.0.0 (currently 2026.428.0)

**Rationale:**

Compass is a strategic orchestrator + UI layer, not an AI system builder. The host Paperclip instance manages per-company agents (CEO, Product, Engineer) and their model bindings. Compass invokes those agents via SDK, applies amendment/cascade logic locally, and persists to host-managed documents + state. SDK already provides every primitive needed:

- `ctx.agents.invoke(agentId, companyId, { prompt })` — fire-and-forget agent wakeup
- `ctx.agents.sessions.sendMessage({ prompt, onEvent })` — streaming chat session
- `ctx.streams.emit("chat", { token })` — UI token push
- Zod re-export for structured output validation
- `ctx.state` (company-scoped) + `ctx.issues.documents` for persistence

Adding LangChain/LangGraph/CrewAI would: (a) violate "no API keys in plugin code" — they all import provider SDKs requiring credentials; (b) break model agnosticism — frameworks couple to integration ecosystems; (c) blow the <200KB bundle target (LangChain alone is 180KB+ gz); (d) duplicate Paperclip's per-company agent abstraction with a parallel agent layer.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph | Adds bundle bloat + abstraction layer over `ctx.agents.invoke`. Only adopt if Compass moves from "invoke host agents" to "define multi-step local agent graphs" — currently premature. |
| LangChain | Couples to provider SDKs (OpenAI, Anthropic). Reintroduces vendor lock-in + key management plugin must not own. |
| Anthropic SDK direct | Locks model vendor; requires plugin-managed API keys; violates Q2/Q3 constraints. |
| Vercel AI SDK | Designed for serverless edge runtimes, not plugin worker contexts. Streaming primitive duplicates `ctx.streams`. |
| CrewAI | Python-only. |
| OpenAI Agents SDK | Vendor lock-in (OpenAI-only); contradicts model-agnostic requirement. |

**Vendor Lock-In Accepted:** No — model choice inherits from host Paperclip instance configuration. Plugin works on any host regardless of provider.

**Hybrid escape hatch:** If a future flow needs reasoning when no `companyId` exists yet (e.g., pre-Found triage), introduce a thin direct-SDK fallback — but keep that path opt-in via plugin config, not the default.

### Entry Point Pattern (Hybrid System Type)

For a Compass-style plugin that invokes host agents and streams results:

```typescript
import { definePlugin, runWorker } from "@paperclipai/plugin-sdk";

const plugin = definePlugin({
  // Initialization: validate SDK availability and register handlers
  async setup(ctx: PluginContext) {
    // Smoke-test: verify host schema (agents, issues, documents)
    const companies = await ctx.companies.list();
    if (companies.length > 0) {
      await Promise.all([
        ctx.agents.list({ companyId: companies[0].id }),
        ctx.issues.list({ companyId: companies[0].id }),
      ]);
    }

    // Register handler: data fetchers
    ctx.data.register("getInventory", async (params: any) => {
      const inventory = await loadInventorySnapshot(ctx, params.companyId);
      return inventory;
    });

    // Register handler: state-mutating actions
    ctx.actions.register("runInterview", async (params: any) => {
      const { companyId, agentId, prompt } = params;
      // Fire-and-forget: invoke host agent with prompt
      const { runId } = await ctx.agents.invoke(agentId, companyId, { prompt });
      return { runId };
    });

    // Register handler: streaming session (conversational)
    ctx.actions.register("sendChatMessage", async (params: any) => {
      const { sessionId, companyId, prompt, onMessage } = params;
      
      const events: AgentSessionEvent[] = [];
      const result = await ctx.agents.sessions.sendMessage(sessionId, companyId, {
        prompt,
        onEvent: (event: AgentSessionEvent) => {
          events.push(event);
          // Relay to UI via streams
          ctx.streams.emit("chat", { event });
          // UI callback
          if (onMessage) onMessage(event);
        },
      });
      return { runId: result.runId, events };
    });
  },

  // Health check for plugin readiness
  async onHealth() {
    return { status: "ok" as const };
  },
});

export default plugin;
runWorker(plugin, import.meta.url);
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| **`PluginContext` (ctx)** | Central interface to host resources. Provides access to agents, state, documents, streams, etc. Capability-gated — calling methods without manifest capability declared throws at runtime. | Every plugin function uses `ctx`. Passed to `setup()`, available to all registered handlers. |
| **`ctx.agents.invoke()`** | Fire-and-forget: wake up a host agent with a prompt. Returns `{ runId }`. No streaming; run executes asynchronously. Perfect for background tasks (apply changes, generate document). | When you want async execution (e.g., "apply this vision to documents in the background"). Good for Found/Assess/Revive/Reposition Apply phases. |
| **`ctx.agents.sessions.sendMessage()`** | Streaming conversational session. Opens a task session, sends prompt, streams `onEvent` callbacks (chunks, status, done, error). For real-time user-facing flows. | When interviewing founder or showing live reasoning (e.g., vision-quest interview, drift analysis with live output). |
| **`ctx.state`** | Key-value store scoped by company + namespace + key. Company-scoped, survives plugin reload, audit-logged. Stores: interview drafts, run state, mode overrides. | Per-company state that must survive restarts. NOT for secrets — never store resolved values, only secret refs. |
| **`ctx.issues.documents`** | Read/write issue documents (versioned, persisted, audit-logged). VISION.md stored here. One doc per issue per key (e.g., "VISION.md", "cascade-plan"). | Storing strategic artifacts (VISION.md, amendment history, cascade plans). Primary persistence mechanism for Compass. |
| **`ctx.streams.emit()`** | Push real-time events from worker to UI via SSE. Named channels; multiple clients can subscribe to same channel. Open channel → emit events → close. | Sending tokens, status updates, or any live feedback to the UI while an action executes. UI side: `usePluginStream("chat")`. |

### Common Pitfalls

1. **Company ID mismatch / cross-company leakage:** `ctx.agents.invoke(agentId, wrongCompanyId, ...)` silently writes to wrong tenant. Always extract `companyId` from request params, validate it matches the requesting user's company. Use `ctx.companies.get(companyId)` early to verify ownership before any mutation. **Fix:** Add early validation: `const company = await ctx.companies.get(companyId); if (!company) throw new Error("Company not found or access denied");`

2. **Ignoring stream close on handler error:** `ctx.streams.emit()` without matching `ctx.streams.close()` leaves the channel open. UI waits forever for `stream:close` event. **Fix:** Always wrap streaming in try-finally: `ctx.streams.open("chat", companyId); try { ... emit ... } finally { ctx.streams.close("chat"); }`

3. **Blocking on `agents.invoke()` when you should stream:** `invoke()` is fire-and-forget — you won't see the agent's output. If you need interactive feedback (interview, reasoning), use `sessions.sendMessage()` with `onEvent` callbacks. Conversely, using sessions for background tasks is wasteful (holds connection open). **Fix:** For background: use `invoke()`. For interactive: use `sessions` with `onEvent`.

4. **Unhandled promise rejection in event handlers:** `ctx.events.on()` or `ctx.agents.sessions.onEvent()` callbacks that throw silently fail. Host doesn't retry. Use try-catch in all event handlers; log errors to `ctx.logger`. **Fix:** `ctx.events.on("issue.created", async (event) => { try { ... } catch (e) { ctx.logger.error(...); } });`

5. **Exceeding context window via state/document bloat:** `ctx.state.set()` and `ctx.issues.documents.upsert()` have no size limits per the SDK, but very large documents (>10MB) or deeply nested state objects can degrade host performance. For Compass, interview drafts + run state should be <1MB each. VISION.md files rarely exceed 500KB. **Fix:** Validate payload size: `if (JSON.stringify(state).length > 1e6) throw new Error("State too large");` Use chunking for very large documents (rare in Compass).

## 4. Implementation Guidance

**Model Configuration:**

Compass does not configure models directly. The host Paperclip instance manages per-company agents (CEO, Product, Engineer, etc.), each with its own model binding and parameters. When Compass invokes an agent:

```typescript
await ctx.agents.invoke(agentId, companyId, {
  prompt: "Interview about revenue model...",
  reason: "Found mode vision-quest",
});
```

The host routes the prompt to the agent's configured model (e.g., Claude Sonnet, GPT-4, etc.) using the host's configured temperature, max_tokens, and system prompt for that agent role. Compass has no control over model choice or parameters — it only constructs the prompt payload.

**Recommendation for Prompts:**
- Keep prompts under 2000 tokens to leave room for agent reasoning
- Use structured few-shot examples (e.g., "Here's an example amendment: `path: /mission, rationale: ...`")
- Never include resolved secrets in prompts — always use secret references via `ctx.secrets.resolve()`
- For interviews: break into smaller sub-questions rather than one monolithic question

**Core Pattern:**

The central pattern for Compass is **structured invocation + validation + persistence:**

```typescript
// 1. Load context (company state, VISION, activity)
const inventory = await loadInventory(ctx, companyId);
const visionContent = await loadVisionDocument(ctx, companyId);

// 2. Construct structured prompt (system role + user question + few-shot)
const prompt = buildInterviewPrompt(
  companyMode,        // "Found" | "Assess" | "Revive" | "Reposition"
  inventory,          // company context
  visionContent,      // current strategic state
  userResponses       // accumulated founder answers
);

// 3a. INTERACTIVE: Streaming session (founder sees live output)
if (isLiveInterview) {
  const session = await ctx.agents.sessions.create(ceoAgentId, companyId);
  const events: AgentSessionEvent[] = [];
  
  await ctx.agents.sessions.sendMessage(session.sessionId, companyId, {
    prompt,
    onEvent: (event: AgentSessionEvent) => {
      events.push(event);
      // Relay chunks to UI
      ctx.streams.emit("interview", { token: event.message });
    },
  });
  
  await ctx.agents.sessions.close(session.sessionId, companyId);
}

// 3b. BACKGROUND: Fire-and-forget (Apply: amendments, provisions, cascade)
if (isApplyStep) {
  const { runId } = await ctx.agents.invoke(ceoAgentId, companyId, {
    prompt: buildApplyPrompt(amendments, vision),
    reason: "Assess mode: apply amendments",
  });
  // Check run status asynchronously or via polling
}

// 4. Validate output (if you get structured response)
const parsed = parseAndValidateResponse(agentOutput, expectedSchema);
if (!parsed.success) {
  ctx.logger.error("Agent output failed validation", { errors: parsed.errors });
  // Retry? Surface to founder? Depends on mode.
}

// 5. Persist artifacts (VISION.md, amendments, findings)
await ctx.issues.documents.upsert({
  issueId,
  key: "VISION.md",
  body: parsedVision.toMarkdown(),
  companyId,
  changeSummary: "Amended: mission + revenue model (Assess mode drift fix)",
});

// 6. Record to engagement history (for later audits)
const { recordFindingsToHistory } = await import("./memory/history-store.js");
await recordFindingsToHistory(ctx, adapter, companyId, runId, "Assess", findings);
```

**Tool Use:**

Compass does not register custom agent tools. Instead, it relies on host-provided tools per agent (CEO, Product, Engineer agents already have tools declared by the host). If Compass needs to contribute tools (e.g., "fetch engagement history"), register them in the manifest + handler:

```typescript
// In manifest.ts:
{
  tools: [
    {
      name: "get-engagement-history",
      displayName: "Get Engagement History",
      description: "Fetch Compass engagement findings for context",
      parametersSchema: {
        type: "object",
        properties: { companyId: { type: "string" } },
      },
    },
  ],
}

// In worker setup:
ctx.tools.register("get-engagement-history", { ... }, async (params, runCtx) => {
  const { getEngagementHistory } = await import("./memory/history-store.js");
  const history = await getEngagementHistory(ctx, adapter, runCtx.companyId);
  return {
    content: JSON.stringify(history || {}),
    data: history,
  };
});
```

Agents (especially CEO) can then call this tool during their reasoning to access Compass findings as context.

**State Management:**

All per-company state lives in `ctx.state` with `scopeKind: "company"`:

```typescript
// Save interview draft
await ctx.state.set(
  {
    scopeKind: "company",
    scopeId: companyId,
    namespace: "compass:found:draft",
    stateKey: "current",
  },
  interviewAnswers // JSON-serializable object
);

// Load interview draft
const draft = await ctx.state.get({
  scopeKind: "company",
  scopeId: companyId,
  namespace: "compass:found:draft",
  stateKey: "current",
});

// Delete draft
await ctx.state.delete({
  scopeKind: "company",
  scopeId: companyId,
  namespace: "compass:found:draft",
  stateKey: "current",
});
```

**Namespace strategy:** Use `compass:{mode}:{flow}` to avoid collisions (e.g., `compass:found:draft`, `compass:assess:run`, `compass:revive:run`). This allows multiple Compass flows to coexist without stepping on each other.

**Context Window Strategy:**

Compass delegates context window management to the host agents. When invoking an agent:

- **Prompt size:** Keep prompts under 2000 tokens to fit within agent context windows (typically 8K–200K depending on host config).
- **Few-shot examples:** Use short, concrete examples (1–2 lines) rather than lengthy templates.
- **Activity snapshots:** In Assess/Revive modes, build a 30-day activity summary (~500 tokens) rather than full issue logs. Use `buildActivitySnapshot(adapter, companyId, 30)` which returns highest-signal items only.
- **VISION.md inclusion:** When amending VISION, include only the sections being modified, not the full 10KB document. Let the agent see context via reference: "current mission statement: `<mission excerpt>`" rather than embedding the whole file.

The host agent will handle token counting and truncation if needed. Plugin responsibility is to avoid obviously bloated payloads (e.g., don't dump 100 raw issues into a prompt; summarize).

### 4b.1 Structured Outputs with Zod

**Definition of the output schema for Compass:**

Compass uses Zod (re-exported from Plugin SDK) to validate agent responses. Example for Assess mode amendments:

```typescript
import { z } from "@paperclipai/plugin-sdk";

// Schema: amendment from drift audit
const DriftAmendmentSchema = z.object({
  sectionId: z.enum([
    "mission",
    "revenue-model",
    "growth-strategy",
    "target-customer",
    "voice",
    "issue-structure",
    "locality",
    "launch-plan",
    "governance",
    "org-structure",
  ]),
  path: z.string().describe("JSON path in VISION.md section, e.g. '/mission/statement'"),
  currentValue: z.string().describe("Existing text from VISION.md"),
  proposedValue: z.string().describe("Suggested replacement"),
  rationale: z.string().describe("Why this change aligns to recent activity"),
  confidence: z.number().min(0).max(1).describe("0.0–1.0 confidence in this amendment"),
});

const DriftReportSchema = z.object({
  items: z.array(DriftAmendmentSchema),
  contextRefreshPreamble: z.string().optional(),
});
```

**Integration with Plugin SDK:**

Compass parses agent output manually (agents return raw text) and validates with Zod:

```typescript
async function detectDrift(
  parsedVision: ParsedVision,
  activity: ActivitySnapshot,
  windowDays: number
): Promise<DriftReport> {
  // Invoke CEO agent with drift analysis prompt
  const { runId } = await ctx.agents.invoke(ceoAgentId, companyId, {
    prompt: `Analyze drift between VISION.md sections and last ${windowDays} days of activity...`,
  });

  // Poll or await run completion (not shown here)
  const result = await pollRunCompletion(runId);
  
  // Parse raw text output as JSON
  let parsed: DriftReport;
  try {
    parsed = JSON.parse(result.outputText);
  } catch (e) {
    ctx.logger.error("Failed to parse agent output as JSON", { outputText: result.outputText });
    return { items: [] }; // Graceful fallback
  }

  // Validate against schema
  try {
    return DriftReportSchema.parse(parsed);
  } catch (validationError) {
    ctx.logger.warn("Agent output failed validation, using partial results", {
      validationError: validationError instanceof Error ? validationError.message : String(validationError),
    });
    // Extract valid items only
    if (Array.isArray(parsed?.items)) {
      return {
        items: parsed.items.filter((item: any) => {
          try {
            DriftAmendmentSchema.parse(item);
            return true;
          } catch {
            return false;
          }
        }),
      };
    }
    return { items: [] };
  }
}
```

**Retry logic:**

When validation fails, Compass has two strategies:

1. **Soft retry (pass-through with partial results):** If 70%+ of items validate, use valid items, log warnings. Good for drift reports (partial amendments are better than nothing).
2. **Hard retry (re-invoke with stricter prompt):** If <30% items validate, re-invoke the agent with "Please output ONLY a JSON array of amendments in this exact format: `[...]`". Max 2 retries; if still failing, surface to founder with a message: "I couldn't parse the amendments. Here's the raw analysis; you can hand-edit."

```typescript
async function validateWithRetry(
  agentOutput: string,
  schema: z.ZodSchema,
  maxRetries: number = 2,
  context?: { agentId: string; companyId: string; prompt: string }
): Promise<{ success: boolean; data: any; errors?: string[] }> {
  let attempts = 0;

  while (attempts <= maxRetries) {
    try {
      const parsed = JSON.parse(agentOutput);
      const validated = schema.parse(parsed);
      return { success: true, data: validated };
    } catch (e) {
      attempts++;
      const errorMsg = e instanceof Error ? e.message : String(e);
      
      if (attempts >= maxRetries) {
        // Max retries exhausted
        ctx.logger.error("Validation failed after max retries", { attempts, errorMsg });
        return {
          success: false,
          data: null,
          errors: [errorMsg],
        };
      }

      // Re-invoke with stricter prompt (only if context provided)
      if (context) {
        ctx.logger.warn(`Validation attempt ${attempts} failed, retrying...`, { errorMsg });
        const stricterPrompt = `${context.prompt}\n\nIMPORTANT: Output ONLY valid JSON. No extra text. Validate against schema: ${JSON.stringify(schema._shape || {})}`;
        const { runId } = await ctx.agents.invoke(context.agentId, context.companyId, {
          prompt: stricterPrompt,
        });
        // Poll for new output and retry parse (code elided)
        agentOutput = await pollRunCompletion(runId);
      }
    }
  }

  return { success: false, data: null, errors: ["Max retries exceeded"] };
}
```

**When to surface:** If validation fails after retries, log the error and return a friendly message to the UI: "I wasn't able to structure the analysis. Here's the raw text; you can refine it manually." This preserves the founder's trust by not silently dropping output.

### 4b.2 Async-First Design

**How async works in the Paperclip Plugin SDK:**

Every SDK method is async-returning Promise. Plugin handlers are async functions:

```typescript
// Data handler (fetch-like)
ctx.data.register("getInventory", async (params: any) => {
  const inventory = await loadInventory(ctx, params.companyId);
  return inventory; // UI waits for this Promise
});

// Action handler (mutation-like)
ctx.actions.register("runApply", async (params: any) => {
  const result = await applyFound(ctx, companyId, vision, preset);
  return result; // UI waits
});

// Event handler (side-effect-like)
ctx.events.on("issue.created", async (event: PluginEvent) => {
  await recordEventToHistory(ctx, event.companyId, event);
  // Fire and forget; host doesn't wait for return
});
```

**The one common mistake: Blocking the event loop with nested `await` chains in handlers.**

If you have a long-running operation (e.g., Apply step), the UI will hang waiting for the handler to return. Use async patterns to avoid this:

```typescript
// WRONG: UI hangs for 30 seconds while apply completes
ctx.actions.register("runApply", async (params) => {
  const result = await applyFound(...); // 30s operation
  return result; // UI finally gets response after 30s
});

// RIGHT: Fire async, return immediately, use streams or polls for progress
ctx.actions.register("runApply", async (params) => {
  const { companyId, vision, preset } = params;
  
  // Launch async work (don't await inside handler)
  (async () => {
    try {
      const result = await applyFound(ctx, companyId, vision, preset);
      // Stream progress/completion
      ctx.streams.emit("apply-progress", { status: "done", result });
    } catch (error) {
      ctx.streams.emit("apply-progress", { status: "error", error: error.message });
    }
  })(); // Fire and forget, no await
  
  // Return immediately
  return { queued: true, runId: globalThis.crypto.randomUUID() };
});

// On UI: poll the stream or status endpoint for updates
```

**Stream vs. Await:**

- **Await (request-response):** Use when UI must block until result. Example: loading inventory, validating form input.
  ```typescript
  ctx.data.register("getInventory", async (params) => {
    return await loadInventory(ctx, params.companyId); // UI waits
  });
  ```

- **Stream (async push):** Use for long-running or real-time updates. Example: interview in progress, draft saving, amendments being applied.
  ```typescript
  ctx.actions.register("runInterview", async (params) => {
    ctx.streams.open("interview", params.companyId);
    const session = await ctx.agents.sessions.create(...);
    
    await ctx.agents.sessions.sendMessage(session.sessionId, companyId, {
      prompt,
      onEvent: (event: AgentSessionEvent) => {
        ctx.streams.emit("interview", { event }); // Push, don't block
      },
    });
    
    ctx.streams.close("interview");
    return { sessionId: session.sessionId }; // Return immediately
  });
  
  // UI side:
  const stream = usePluginStream("interview", { companyId });
  // Receives events in real-time, no blocking
  ```

## 5. Evaluation Strategy

### Dimensions

Grounded in domain rubric ingredients (Section 1b), not generic labels. Each dimension maps to founder-facing trust.

| Dimension | Rubric (Pass/Fail Criteria in Domain Language) | Measurement Approach | Priority |
|-----------|----------------------------------------------|----------------------|----------|
| **1. Mission-Activity Alignment Clarity** | **PASS:** Compass names exact mismatch with specific dates, issue/PR titles, and quantified effort (e.g., "70% on SDK integrations; VISION says focus on product; estimated 2 weeks sunk"). Flags include founder context check (e.g., "Is this intentional testing for new market?") to avoid drift hallucination. **FAIL:** Vague language ("suboptimal resource allocation"). Flags drift that contradicts founder's known intent. Doesn't distinguish between goal-less activity vs. strategic pivot. | LLM Judge (calibrated against YC partner verdicts) + Code (drift score validation: score ≥ 0.7 = pass) | Critical |
| **2. Actionability of Amendments** | **PASS:** Amendment specifies exact section path in VISION.md, rationale with supporting evidence (falsifiable), approval routing (founder-only or founder+CEO). Proposed change is scoped (reframe GTM, not pivot entire company). **FAIL:** Vague direction ("consider reframing..."). Change so major it requires full re-interview. Ignores sunk cost / team capability. Buries change in prose instead of structured JSON. | Code (schema validation: path, rationale, confidence present; text length 50-500 chars) + LLM Judge (falsifiability + scope check) | Critical |
| **3. Stall Diagnosis Accuracy** | **PASS:** Compass narrows stall cause to one of: decision-fatigue, agent underperformance, founder burnout, cross-agent misalignment, scope creep. Includes evidence: specific issue numbers, heartbeat timestamps, founder activity delta. **FAIL:** Vague "momentum lost". Attributes to "bad market" without agent-delivery check. Recommends pivot as solution to decision-fatigue stall. Misses founder burnout signals (2+ week Slack absence, emotional flattening). | Code (classifier confidence ≥ 0.8, mandatory evidence fields populated) + Human (burnout signal detection requires org-coach validation) | High |
| **4. Avoiding Premature Pivots** | **PASS:** If recommending pivot, names (a) what was working with metrics (ARR, retention), (b) why no longer sufficient, (c) core capability transfer. Only recommends if ≥2 criteria met. Includes "no-pivot, reframe mission" alternative. Checks cash runway. **FAIL:** Recommends pivot due to 3-week no-ship (stall problem, not strategy). No cash runway check. Contradicts founder's stated interests. Inconsistent (flagged "drift" iteration N, suggests "pivot" iteration N+1). | LLM Judge (evidence sufficiency against YC partner checklist) + Code (consistency check: no "drift" → "pivot" flip within 30 days) | High |
| **5. Cascade Plan Feasibility** | **PASS:** Lists issues in order, assigns agent per issue, estimates 2-week throughput per agent, names risks/blockers, specifies fallback if agent times out. Plan is testable (founder can sample one issue, verify agent executes). **FAIL:** Prose paragraph. 10+ issues unprioritized. Requires agent coordination without naming dependencies. Assumes agents need zero founder input. No fallback strategy. | Code (JSON schema: issues, agent assignments, throughput estimates, blockers, fallback all present) + Human (feasibility check: org coach reviews for founder-load assumption) | High |
| **6. Schema Compliance + No Hallucination** | **PASS:** All agent outputs match expected Zod schema (amendments have path/rationale/confidence; drift reports have items array; cascade has issues array). No unresolved placeholders in VISION. No cross-company `companyId` mismatch. **FAIL:** Output doesn't parse as JSON. Missing required fields. VISION contains {{placeholder}} after Apply. Data written to wrong company. | Code (Zod validation ≥95%, schema parse success rate, companyId matching on all writes) | Critical |
| **7. Safety: No Cross-Company Leakage** | **PASS:** All `ctx.agents.invoke`, `ctx.state.set`, `ctx.issues.documents.upsert` calls include correct `companyId` extracted from request params. Early validation: `const company = await ctx.companies.get(companyId)` succeeds before any mutation. **FAIL:** Silent companyId mismatch. No validation before write. Data visible in wrong company's history. | Code (audit log review: all writes tagged with correct companyId; test coverage ≥95% for companyId validation) | Critical |
| **8. Stream Integrity + Partial Response Handling** | **PASS:** Streaming sessions complete (no orphan channels). On stream error, gracefully resume or surface "Interview interrupted; click Resume to continue." Founder never sees half a question. State persists partial answers. **FAIL:** Stream drops mid-interview, no resume path. Founder sees incomplete response. State lost on error. | Code (stream open/close balance ≥99%; error recovery test) + LLM Judge (UI message clarity under stream failure) | High |

### Reference Dataset

**Size:** 20 examples minimum (10 for alpha, expand to 20 for v1 release, 50+ for production).

**Composition:**

| Scenario Type | Count | Critical Success Path |
|---------------|-------|----------------------|
| **Found Mode** | 3 | Vision-quest interview → VISION.md generation → agent provisioning → baseline heartbeat |
| **Assess Mode: Drift Detection** | 4 | Clean drift detection (aligned activity + mission match; misaligned activity + mission mismatch; intentional pivot; marginal drift) |

**Edge Cases & Failure Modes:**
- Stream loss mid-interview (partial response recovery)
- Cross-company leakage scenario (founder A's company data leaked to company B)
- Drift hallucination (advisor flags "drift" that matches founder's intent)
- Idempotency violation (same amendment queued twice)

**Labeling:**

1. **Domain Expert Labeling (primary):** 2-3 YC partners or startup advisors label 10-15 scenarios per dimension with expected guidance. Example: "If you were consulting this company showing drift X, would you flag it? Why?" Reference labels serve as ground truth for LLM judge calibration.
2. **LLM Judge Calibration:** Compare Compass output to domain expert labels. Measure correlation ≥0.7 before trusting LLM judge on unseen data.
3. **Automated Labeling (secondary):** Code-based checks (schema validation, companyId matching, placeholder detection) require no expert input.

**Creation Timeline:**
- Week 1-2 (concurrent with Found mode implementation): Gather 5 real company scenarios (VISION.md + 30-day activity) from Paperclip founder's own companies.
- Week 3-4 (Assess mode): Expand to 10 scenarios; add artificial edge cases (stream dropout, cross-company test).
- Week 5-6 (Revive + Reposition): Complete 20-example reference dataset; recruit 2 domain experts for calibration.
- Week 7+ (production): Expand based on real failure modes observed in production; re-calibrate LLM judge monthly.

## 6. Guardrails

### Online (Real-Time)

Run on every request. Failures block or escalate immediately.

| Guardrail | Trigger | Intervention | Latency Budget |
|-----------|---------|--------------|-----------------|
| **Schema Validation** | Agent output fails Zod parse (JSON malformed, required field missing) | Log error, surface to founder: "I couldn't parse the response. Here's the raw text; you can refine manually." Do NOT apply amendments or create issues silently. | <100ms |
| **Cross-Company CompanyId Validation** | `ctx.companies.get(companyId)` returns null or access denied | Immediately reject handler, log security event, escalate to Paperclip host. | <50ms |
| **Idempotency Key Deduplication** | Agent wakeup request with same `idempotency_key` + `reason` received within 5 minutes of prior successful invocation | Return cached result, skip second invocation. | <10ms (state lookup) |
| **VISION Placeholder Detection** | Generated or amended VISION.md contains unresolved {{placeholder}} | Block Apply step, require founder to fill placeholders manually or re-interview. Message: "Missing sections: [list]. Please complete the vision-quest interview." | <50ms |
| **Stream Integrity Check** | `ctx.streams.open()` without matching `ctx.streams.close()` within 60 seconds | Auto-close orphan stream, log warning, notify UI: "Interview was interrupted. Click Resume to continue from where you left off." | <1s |

### Offline (Flywheel)

Run daily or weekly on sampled interactions. Feed improvement loop.

| Metric | Sampling Strategy | Action on Degradation | Recalibration Frequency |
|--------|------------------|----------------------|--------------------------|
| **Drift Detection Hallucination Rate** | Sample 10% of all Assess mode runs. LLM judge scores drift report against domain expert rubric (0 = hallucination, 1 = valid). Target ≥0.85. | If <0.85: review failed cases with YC partner, retune drift-detection prompt (few-shot examples, confidence thresholds). | Monthly |
| **Amendment Actionability Score** | Sample 20% of amendments. LLM judge scores against "can founder execute this?" rubric (path clarity, rationale quality, scope). Target ≥0.8. | If <0.8: adjust amendment-generation prompt to require "falsifiable rationale" and "scope cap at single VISION section". | Monthly |
| **Cascade Plan Feasibility Rate** | Sample all cascade plans (rare, low volume). Human org coach reviews for founder-load assumption. Target 100% feasible (no "agent-only" assumptions unsupported by agent capabilities). | If <100%: adjust cascade-generation prompt to explicitly name founder handoff points. | Per-release |
| **Stall Diagnosis Recall** | Quarterly: compare Compass stall diagnoses from 3 months prior against founder's actual outcome. Did Compass identify the real root cause? Target ≥0.8 recall. | If <0.8: add missing failure mode (e.g., founder burnout signals) to classifier training data. Re-interview domain experts. | Quarterly |
| **Schema Validation Success Rate** | Track `Zod.parse()` success rate across all agent outputs. Target ≥0.99. | If <0.99: (1) soft-retry with stricter prompt (JSON-only output), (2) surface raw text to founder as fallback. Log prompt that failed to drive prompt-engineering iteration. | Daily (automated alert if <0.95) |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (self-hosted or managed)

Compass emits traces via OpenTelemetry. Phoenix ingests and visualizes invocation → validation → persistence pipeline. Traces include:
- `companyId`, `mode`, `agentId`, `prompt`, `outputText`, `validationResult`, `driftItemCount`, etc.
- Latency per stage (agent invocation, JSON parse, Zod validation, document write)
- Error events (stream drop, companyId mismatch, schema violation)

**Key Metrics to Track:**

1. **Agent Invocation Success Rate** — % of `ctx.agents.invoke()` or `ctx.agents.sessions.sendMessage()` that complete without error. Target ≥99%. Alert if <98% over 1-hour rolling window.

2. **Schema Validation Success Rate** — % of agent outputs that pass Zod schema validation on first attempt. Target ≥97%. Alert if <95%; triggers prompt engineering review.

3. **Amendment Application Rate** — % of proposed amendments that founders approve + apply (proxy for trust). Target ≥70% for Assess mode. If <60%, investigate: are amendments too vague? Do founders trust drift detection?

4. **Cascade Plan Execution Rate** — % of issues in cascade plans that agents actually execute within 2 weeks. Target ≥75%. Alert if <60%; indicates plan feasibility or agent capability mismatch.

5. **Drift Detection Precision** — Monthly: YC partner spot-checks 5-10 Assess mode outputs. How many flagged drifts do they agree are valid? Target ≥0.9. If <0.85, retune prompt + recalibrate LLM judge.

6. **User Satisfaction (NPS proxy)** — Quarterly founder survey: "How useful was Compass's diagnosis/amendment/plan?" Score 1-10. Target ≥7. Track per mode.

7. **Latency: Agent Invocation** — Time from `ctx.agents.invoke()` to agent response. Target <5s queueing, <30s execution for Assess/Revive, <3s per token for Found interviews. Alert if >10s queueing.

8. **Security: CompanyId Validation** — Count of `ctx.companies.get(companyId)` rejections per day. Target = 0 (all validation passes). Any non-zero = incident.

**Alert Thresholds:**

| Metric | Severity | Threshold | Action |
|--------|----------|-----------|--------|
| Schema Validation Success Rate | Critical | <95% for 1h | Page on-call, review agent prompt + Zod schema mismatch |
| Cross-Company CompanyId Validation Failures | Critical | ≥1 rejection | Immediate incident: audit logs, notify affected founders, hotfix validation logic |
| Stream Integrity (orphan channels) | High | >5 per day | Review error handling in streaming handlers |
| Amendment Application Rate | Medium | <60% rolling 7d | Schedule YC partner review of amendment clarity |
| Cascade Plan Execution Rate | Medium | <60% rolling 14d | Review plan feasibility + agent capability assumptions |
| Agent Invocation Latency | Medium | >10s queueing, >60s execution | Investigate host agent health, check prompt token bloat |

**Smart Sampling Strategy:**

Not all interactions warrant deep review. Sample by signal strength:

1. **Mandatory Human Review (100% sampled):**
   - Any founder who marks amendment/cascade as "unhelpful" or "incorrect"
   - Any cross-company leakage detection (security incident)
   - Stall diagnosis where founder later reports it was wrong

2. **Sampled Review (20% stratified):**
   - High-confidence drifts (Compass confidence ≥0.9) — verify 1 in 5
   - Low-confidence drifts (Compass confidence <0.6) — verify 4 in 5 (high-risk signal)
   - New amendment types (e.g., first time recommending pivot) — verify 100%

3. **Quarterly Deep Dive (per-founder):**
   - Every founder with Compass-active company: review 3-month history. Did recommendations drive outcomes? Did Compass miss real problems?
   - Feed findings back into rubric calibration + prompt tuning.

4. **Automated Sampling (no human review):**
   - Schema validation passes ✓
   - CompanyId matches ✓
   - Stream completed successfully ✓
   - → Log only; no escalation needed

**Tracing Configuration Example:**

```typescript
// In src/worker.ts, after definePlugin setup():
import { trace, context } from "opentelemetry-api";

const tracer = trace.getTracer("compass-plugin");

// Wrap each mode handler
async function assessMode(ctx, companyId, modeOverride) {
  const span = tracer.startSpan("assess-mode", {
    attributes: {
      companyId,
      modeOverride,
      timestamp: Date.now(),
    },
  });

  return context.with(trace.setSpan(context.active(), span), async () => {
    try {
      // 1. Load context
      const inventory = await loadInventory(ctx, companyId);
      const visionContent = await loadVisionDocument(ctx, companyId);
      const activity = await buildActivitySnapshot(ctx, companyId, 30);

      // 2. Invoke agent
      const driftSpan = tracer.startSpan("invoke-drift-detection", {
        parent: span,
        attributes: { agentId: "ceo" },
      });

      const driftReport = await invokeAgentForDrift(ctx, companyId, visionContent, activity);
      driftSpan.setAttributes({ driftItemCount: driftReport.items.length });
      driftSpan.end();

      // 3. Validate
      const validationSpan = tracer.startSpan("schema-validation", { parent: span });
      const validated = DriftReportSchema.parse(driftReport);
      validationSpan.setAttributes({ success: true });
      validationSpan.end();

      // 4. Persist
      const persistSpan = tracer.startSpan("persist-findings", { parent: span });
      await persistFindings(ctx, companyId, validated);
      persistSpan.end();

      span.setAttributes({
        status: "success",
        amendmentCount: validated.items.length,
      });
    } catch (error) {
      span.recordException(error);
      span.setAttributes({ status: "error" });
      throw error;
    } finally {
      span.end();
    }
  });
}
```
