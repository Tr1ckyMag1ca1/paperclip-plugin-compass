**Create `src/assess/drift.ts`** — Drift detection per D-01, D-03, D-04:
- Export `detectDrift(vision: ParsedVision, activity: ActivitySnapshot, windowDays: number = 30): DriftReport`
- **Confidence scoring blend (D-04, Claude's discretion):**
  1. **Lexical score** (0..1): Keyword overlap. For each VISION section, extract key terms (nouns, verbs, proper names). Count how many terms appear in activity items. Score = matches / total_terms, capped at 1.0.
  2. **Semantic score** (0..1): Evidence clustering. For each section, count distinct activity items that mention the section topic area. Score = (distinct_items / total_items_in_window), normalized to 0..1.
  3. **Recency score** (0..1): Weighted by time. Recent activity (last 7 days) weighted 1.0, 7–14 days: 0.8, 14–30 days: 0.5. Average across all evidence items.
  4. **Final confidence = (lexical × 0.4) + (semantic × 0.4) + (recency × 0.2)** — balanced toward evidence quality + clustering.
- For each VISION section, generate at most one `DriftItem` if confidence >= 0.5 threshold (D-04). Below 0.5, item deferred (not surfaced to founder in v1 per D-04 specifics).
- Per drift item, populate `severity` as: confidence >= 0.75 → 'blocker', confidence >= 0.5 → 'warn', < 0.5 → 'info' (deferred).
- `proposedAmendment` starts as placeholder markdown delta. Exact amendment text will be authored during preview (Phase 3 UI will let founder edit). For now, amendment = "Review the following activity and consider updating this section: {evidence summary}".
- Return `DriftReport` with items, runId (UUID), generatedAt timestamp, company_id.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Activity input (SDK adapter → drift detector) | Issue/comment/document data from Paperclip DB — trusted via SDK validation; drift detector is pure transform |
| VISION.md parsing | User-provided markdown; parser extracts structure deterministically without code execution |
| Amendment proposals | Generated deterministically; no user code eval |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Spoofing | Activity data source attribution | Mitigate | Activity items include authorId from SDK; not validated at drift layer (SDK guarantees auth). Cascade step (Plan 4) will validate agent existence before issue creation. |
| T-03-02 | Tampering | VISION.md roundtrip | Mitigate | Round-trip test enforces parse(serialize(parse(x))) === parse(x); any unintended mutation fails CI. Serialization is deterministic (section order fixed). |
| T-03-03 | Repudiation | Amendment changelog | Mitigate | Changelog entries include ISO timestamp + founderIdentity (if SDK exposes); cannot be edited retroactively (immutable append-only). Phase 6 audit trail will extend. |
| T-03-04 | Information Disclosure | Activity query filtering | Mitigate | listDocuments filters out VISION.md to prevent self-reference artifact in drift report. Company_id is scoped at SDK level (caller-provided). |
| T-03-05 | Denial of Service | Drift detection perf | Accept | Drift detector is O(n·m) on activity items × vision sections; capped by 30-day window (max ~500 issues/comments). No unbounded loops. Will timeout with alert if activity > 10K items (not enforced in v1, acceptable risk per PROJECT.md constraints). |

</threat_model>
