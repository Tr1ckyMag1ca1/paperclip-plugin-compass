  <name>Task 1: WCAG AA contrast audit for status badges and semantic colors (UIV-03)</name>
  <files>docs/WCAG_AUDIT.md</files>
  <action>
Execute WCAG AA contrast audit for all status badges and semantic color uses across Phase 10 memory components. Document all measurements in docs/WCAG_AUDIT.md. Target: ≥4.5:1 contrast ratio in both light and dark modes.

**Components to audit:**

Status badges (FindingStatusBadge):
- Status: "open" (red/error semantic color)
- Status: "addressed" (emerald/success semantic color)
- Status: "invalidated" (slate/neutral semantic color)

Mode badges (ModeBadge):
- Mode: "Found" (emerald)
- Mode: "Assess" (blue)
- Mode: "Revive" (red)
- Mode: "Reposition" (yellow)

**Methodology:**

1. **Light mode audit:**
   - Render each badge variant in light background (bg-card)
   - Use WebAIM Contrast Checker (https://webaim.org/resources/contrastchecker/) or browser axe DevTools extension
   - Measure text color (e.g., text-emerald-500) against background (e.g., bg-emerald-500/10)
   - Record ratio; flag if <4.5:1

2. **Dark mode audit:**
   - Force `.dark` class in browser DevTools
   - Re-render each badge variant
   - Measure colors again (CSS variables may adjust for dark mode)
   - Record ratio; flag if <4.5:1

3. **Audit checklist (example for FindingStatusBadge "open" status):**
   ```
   FindingStatusBadge Status: "open"
   
   Light mode:
   - Component: <span className="inline-block px-1 py-1 rounded-full text-xs font-bold bg-red-500/10 text-red-500">Open</span>
   - Measured colors: text-red-500 (#ef4444) on bg-red-500/10 (rgba(239, 68, 68, 0.1) ≈ #f9ecec)
   - Contrast ratio: 7.2:1 ✓ WCAG AAA (exceeds AA requirement of 4.5:1)
   - Status: PASS
   
   Dark mode:
   - Same component tree, but colors adjusted via CSS custom properties
   - Measured colors: text-red-500 (adjusted for dark theme) on bg-red-500/10 (adjusted)
   - Contrast ratio: 5.1:1 ✓ WCAG AA
   - Status: PASS
   ```

4. **Document all results in docs/WCAG_AUDIT.md:**
   - Create table with columns: Component, Status/Mode, Light Mode Ratio, Dark Mode Ratio, Pass/Fail
   - Include any failed badges with remediation notes (if applicable)
   - Summary: All badges meet WCAG AA (≥4.5:1) in both themes

5. **Tools:**
   - WebAIM Contrast Checker (online, or browser extension)
   - axe DevTools Chrome extension (accessibility audit + contrast)
   - Firefox Accessibility Inspector (built-in)
   - Chrome DevTools Accessibility panel (Color Contrast section)

6. **If any badge fails contrast:**
   - Document the issue
   - Propose remediation (adjust color, increase opacity, change background)
   - Do NOT proceed with Wave 3 until all badges pass WCAG AA

**Reference:** RESEARCH.md "UIV-03: WCAG AA Contrast Verification" section for detailed methodology.
  </action>

  <name>Task 2: Production build verification with Tailwind JIT purge analysis (UIV-04)</name>

  <action>
Execute production build (pnpm build) and verify Tailwind JIT purge correctness, missing-class detection, and bundle integrity. Document all checks in docs/BUILD_VERIFICATION.md. Target: zero missing-class errors, all used utility classes present in final bundle.

**Verification steps:**

1. **Pre-build state check:**
   - Confirm all token migrations from Wave 1 are present in source
   - Confirm no template-literal color generation (e.g., `className={`bg-${color}`}`)
   - Run grep to verify zero broken tokens: `npm run verify:broken-patterns`

2. **Execute production build:**
   ```bash
   pnpm build
   ```
   - Capture full build log (stdout + stderr)
   - Verify exit code 0 (success)
   - Note any warnings about missing CSS classes or Tailwind issues

3. **Tailwind JIT analysis:**
   - Inspect `dist/ui/index.css` (or equivalent Tailwind output)
   - Confirm all spacing classes used in Phase 10 components are present:
     - Spacing: gap-1, gap-2, gap-3, gap-4, px-1 through px-4, py-1 through py-4, mt-1, mt-2, mt-4, mt-6, pb-2
     - Typography: text-xs, text-sm, text-base with font-medium, font-semibold, font-bold weights
     - Colors: emerald-500, red-500, yellow-500, blue-500, and opacity variants (/10, /20)
   - Verify JIT did NOT purge any used classes (all above classes should be in final CSS)

4. **Bundle integrity check:**
   - Confirm `dist/ui/index.js` is valid JavaScript (no syntax errors)
   - Check file size: `ls -lh dist/ui/index.js` (estimate before gzip)
   - Generate gzip size: `gzip -c dist/ui/index.js | wc -c` (measure in bytes)
   - Verify bundle loads in browser without runtime errors

5. **Runtime verification (optional, if dev Paperclip host available):**
   - Load built plugin in local Paperclip instance
   - Render HistoryPanel, FindingCard, ScheduleRoutineRow
   - Confirm no missing classes, no layout collapse, no color issues
   - Verify both light and dark modes render correctly

6. **Document findings in docs/BUILD_VERIFICATION.md:**
   - Build timestamp, pnpm version, Node version
   - Build exit code: 0 (success)
   - Broken patterns verifier: 0 hits
   - Tailwind JIT cache: valid (no purge warnings)
   - Bundle size: X bytes uncompressed, Y bytes gzipped
   - CSS classes verified: ✓ (list key classes confirmed in output)
   - Runtime test: ✓ (if applicable)
   - Summary: Production build PASSED ✓

7. **If build fails:**
   - Capture full error message
   - Diagnose root cause (missing class, build config issue, etc.)
   - Fix in codebase (likely a broken token escape in Task 1/2)
   - Re-run pnpm build
   - Do NOT proceed until build succeeds with 0 errors

**Reference:** RESEARCH.md "UIV-04: Production Build Verification" section for methodology. See 07-RESEARCH.md "Tailwind JIT Constraints" for background on dynamic class generation risks.
