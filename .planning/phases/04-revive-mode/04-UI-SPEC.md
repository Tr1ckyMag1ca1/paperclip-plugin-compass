# Phase 4 — Revive Mode UI Design Contract

> Visual and interaction contract for Revive Mode stall diagnosis, action queue, incremental apply flow, and sample-pivot pattern. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Paperclip host design tokens only |
| Preset | not applicable |
| Component library | Plugin SDK UI components (MetricCard, StatusBadge, DataTable, LogView, ActionBar) |
| Icon library | Lucide React (^1.14.0) |
| Font | Inherited from Paperclip host (no custom font stack) |

**Notes:**
- Inherits Phase 2 + Phase 3 design system entirely (same spacing scale, typography, color system, class naming)
- No additional third-party component registry — Plugin SDK UI only
- Reuses Phase 2/3 components: `ConfirmationModal.tsx`, `ApplyProgress.tsx`, `ApplyErrorDisplay.tsx`, `CustomOverrideWarning.tsx`

**Exceptions (Phase 4 specific):**
- ActionItemCard padding: `p-md` (16px)

- Sidebar width constraint: ~360px — no horizontal scrolling

## Priority Badge Styling (Phase 4 Visual)

ActionItemCard displays a priority indicator (inline badge at card header left):

- **Low priority** (0–0.33): Gray background, `bg-card` with `text-foreground` text
- **Medium priority** (0.33–0.66): Amber/accent color, `bg-accent/20` with `text-accent` text, weight 600
- **High priority** (0.66–1.0): Red/destructive color, `bg-destructive/20` with `text-destructive` text, weight 700

Badge shows short text: "P0" (high), "P1" (medium), "P2" (low) OR full words "High", "Medium", "Low" (planner decides).

## Interaction Patterns

### RevivePanel Layout (Main Entry Point)

**Header** (fixed at top, sticky):
1. **Company Name** — left-aligned, `text-display font-bold`
2. **Stall Summary Badge** — centered below company name, `text-label` gray text with optional destructive accent highlight. Shows "Stalled — {N} days no activity, {N} blocker(s)"
3. **Action Buttons** (right-aligned):
   - "Find what's blocking this company" button (primary) — opens diagnosis flow (disabled if diagnosis already in progress; shows spinner)
   - "Discard" text button (secondary, gray) — only appears if diagnosis in progress

**Helper text** (below header, light gray `text-foreground/70`):
"Fix what's blocking this company"

**Main content area** (scrollable):
- **If no diagnosis in progress:** Empty state with heading "This company isn't stalled" + body text + "Try Assess" link
- **If diagnosis running:** Loading indicator with text ("Diagnosing…")
- **If diagnosis complete:** ActionQueuePanel (see below)
- **If diagnosis cached/paused:** Resume notification + same ActionQueuePanel

**Sticky footer** (fixed at bottom, `bg-card` background with top border):
- Left: "Progress: {N} of {N} addressed" in `text-label` gray
- Center: "{N} action(s) pending" in `text-body`
- Right: "Review and apply" button (enabled only if ≥1 item addressed, otherwise grayed out with "Address blocking items to continue")

---

### ActionQueuePanel Structure

**Grouping by cause:**
- All action items grouped under their respective cause headers
- Cause header format: "{Cause name}" in `text-heading font-bold`
- Cause names (5 categories from CONTEXT.md): "Stuck on a blocker", "Drifted from vision", "Integration broken", "Stuck in approval loop", "Agent stopped responding"
- Causes appear in priority order (highest-impact causes first)
- Empty causes (no items) hidden

**Per-action-item card layout:**

1. **Card header** (padded `p-md`, light `bg-card` background, flex row):
   - Left: Priority badge (`p-xs`, color-coded: high=destructive, medium=accent, low=gray)
   - Center-Left: Action title in `text-body font-bold`
   - Right: Status indicator in `text-label` (e.g., "pending", "✓ addressed", "× dismissed")

2. **Card body** (padded `p-md`, white/background):
   - **Consequence section** (h4 heading in `text-label font-normal`, optional):
     - "Unlocks {N} downstream issue(s)" OR "Restores agent {name}"
     - Shown in `text-foreground/70` gray

   - **What it is section** (brief description):
     - Plain text in `text-body`, 1–2 sentences max
     - Example: "This issue has been stuck for 16 days and blocks 3 downstream work items."

   - **Action buttons** (flex row below description):
     - Primary CTA button (accent style, full-width or auto): "{Verb} {noun}"
       - Examples: "Replace issue", "Reassign to Alice", "Brief the agent", "Switch to sample mode", "Mark resolved", "Restart agent"
     - Secondary buttons (text-only, gray):
       - "Dismiss" (small text button)
       - "Explain" (small text button, opens collapsible with heuristic details)

3. **Collapsible explanation** (if "Explain" clicked):
   - Shows heuristic details in `text-body` with light gray background
   - Example: "This issue has been stuck for 16 days without update, and 3 other issues are waiting for it to resolve."

---

### Per-Action Confirmation Modal (Incremental Apply Gate)

Triggered by clicking primary CTA on ActionItemCard. **Single confirmation step** (lighter than Phase 2/3 two-stage gate).

**Modal header:** "Apply this action?"

**Modal body:**
```
{Action title}

{What's unblocked}

This will:
- {Specific write 1} (e.g., "Update Issue #47")
- {Specific write 2} (e.g., "Create 1 downstream issue")
- {Specific write 3} (e.g., "Queue 1 wakeup")
```

**Buttons:**
- "Cancel" (secondary) — closes modal, returns to action queue
- "Apply" (primary, accent) → runs action handler, updates card status to "addressed"

---

### Sample-Pivot Modal (Special Action)

Triggered by "Switch to sample mode" CTA on an ActionItemCard.

**Modal header:** "Switch to sample mode for this issue"

**Modal body:**
```
We'll keep your current draft as a sample to critique, and open a fresh 
production issue for the improved version. This is a known pattern from 
how vision-quest companies unstick themselves.

[SAMPLE_PIVOT.md explanation doc will be created]
```

**Buttons:**
- "Cancel" (secondary) — closes modal
- "Create sample & production" (primary, accent) → runs sample-pivot handler

**After apply, inline result in ActionItemCard:**
```
✓ Issue #[sample] created as [SAMPLE]
✓ Issue #[production] created as [PRODUCTION]  
✓ SAMPLE_PIVOT.md doc created
```

---

### Per-Action Apply Progress (Sequential, Not Modal)

When founder clicks "Apply" on an action, progress appears as overlay or inline expansion (planner decides):

**Sequential step indicator:**
```
Validating setup…
✓ Preflight checks
Applying action…
✓ Issue #47 updated
Creating cascading issues…
✓ 1 downstream issue created
Queuing wakeups…
✓ 1 agent wakeup queued
```

Each step shows:
- Status: "…" (in-progress) or "✓" (complete)
- Step name + optional result

**On success:**
```
✓ Action applied!

Issue #47 replaced with Issue #92.
This unblocks 3 downstream items.

[OK] or auto-close after 2s, return to action queue
```

**On failure at any step:**
```
Apply failed: {Step name}

Error: {Readable error message}
Next step: {Recovery instruction}

Rollback (if applicable):
✓ Cascading issues deleted
✓ Original issue restored

[Retry] | [Close]
```

### Agent Screening & Custom Override Warning (Reused from Phase 3)

During Apply preview (if any action creates new issues/wakeups), show CustomOverrideWarning for affected agents:

**Warning card** (light red/amber background via `border-destructive` or `bg-card` with left border `border-l-4 border-destructive`):

```
⚠️ Agent [Agent name] has custom instructions

This agent's instructions have been customized beyond the preset baseline.
The cascading issue will be created, but the agent's custom overrides 
will not be automatically merged.

Review the following before applying:
[Show diff of what would be added vs agent's custom config]

☑️ I've reviewed the override conflict and approve cascading anyway
```

Checkbox-style confirmation required before allowing action to proceed.

---

### Empty Revive State

When founder triggers Revive on a healthy company (no stall detected):

**Main content area (scrollable, centered):**

**Heading:** "This company isn't stalled" in `text-heading font-bold`

**Body text:** "No blocking issues detected. Try Assess for a strategic audit instead." in `text-body`

**Action buttons:**
- "Try Assess mode" link (accent colored, underlined)
- "Go back" link (gray)

---

### Resume Revive State

If founder returns to Revive panel after partial diagnosis review:

**Notification** (light `bg-card` background, `p-md` padding):
```
Resume: {N}% progress, {N} action items found

[Resume diagnosis] | [Start over]
```

Then show ActionQueuePanel with cached results.

## Accessibility

- All interactive elements keyboard-navigable (Tab, Enter, Space)
- Priority badge has `aria-label="Priority: High"` or equivalent
- Action buttons have clear `aria-label` for screen readers
- Confirm modal has `aria-labelledby` and `aria-describedby` linking to modal header + body
- Modal backdrop blocks background interaction (focus trap)
- Collapsible "Explain" section has `aria-expanded="true|false"`
- Color-coded priority badges must have text label fallback (never color-only)
- Error messages linked to relevant action cards via `aria-describedby`

## Designer Notes (Claude's Discretion)

This contract locks the **what** (behavior + copy + visual relationships) but leaves **where** for the planner:

1. **Priority badge format** — "P0/P1/P2" vs "High/Medium/Low"? Recommendation: "High/Medium/Low" (more founder-readable), but planner may prefer compact "P0/P1/P2".
2. **Per-action progress visibility** — inline expansion in ActionItemCard vs modal overlay vs full-panel? Recommendation: inline expansion (less disruptive context switch), but modal acceptable if space tight.
3. **Cause section collapsibility** — all expanded by default, or collapsed? Recommendation: all expanded (founder scans full queue at once), but planner may collapse low-priority causes to reduce cognitive load.
4. **Sticky footer position** — fixed bottom (current) vs inline after queue? Recommendation: fixed bottom (persistent progress visibility, matches Phase 2/3).
5. **Agent screening UI** — shown inline during apply, or modal overlay? Recommendation: modal overlay (cleaner context), matches Phase 3 CustomOverrideWarning pattern.

All above locked in **planner** phase per Phase 1 UI-SPEC.md conventions. UI-SPEC provides the contract; planner places components.
