# Phase 6 — Engagement Memory + Scheduled Check-ins UI Design Contract

> Visual and interaction contract for persistent engagement history, finding status tracking, and scheduled routine management. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Paperclip host design tokens only |
| Preset | not applicable |
| Component library | Plugin SDK UI components (MetricCard, StatusBadge, DataTable, LogView, ActionBar) |
| Icon library | Lucide React (^1.14.0) |
| Font | Inherited from Paperclip host (no custom font stack) |

**Notes:**
- Inherits Phase 2 + Phase 3 + Phase 4 + Phase 5 design system entirely (same spacing scale, typography, color system, class naming)
- No additional third-party component registry — Plugin SDK UI only
- Reuses Phase 2/3/4/5 components: CardLayout pattern from Phase 4 ActionItemCard, StatusBadge styling from Plugin SDK

## Spacing Scale

**Inherited from Phase 2 (unchanged):**

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, badge padding, status-change button gaps |
| sm | 8px | Compact element spacing, finding card list gaps, filter control gaps |
| md | 16px | Default element spacing, finding card padding, schedule item padding |
| lg | 24px | Section padding, history panel padding, form section spacing |
| xl | 32px | Layout column gaps, panel padding |
| 2xl | 48px | Major section breaks, panel boundaries |
| 3xl | 64px | Full-page top/bottom spacing (sidebar width constraint) |

**Exceptions (Phase 6 specific):**
- HistoryPanel header (sticky): `p-lg` (24px)
- FindingCard padding: `p-md` (16px)
- Evidence chip gap: `gap-xs` (4px between chips, reuse from Phase 3)
- Status badge padding: `px-xs py-xs` (4px inline, 2px vertical)
- Schedule list item gap: `gap-sm` (8px between routine rows)
- Filter control gap: `gap-sm` (8px between status/mode/date filter buttons)
- Sidebar width constraint: ~360px — no horizontal scrolling

## Interaction Patterns

### MainPanel Tab Structure (Phase 6 Integration)

**Tab headers** (horizontal tabs or vertical rail in MainPanel):
1. "Found" (or "Found Mode") — existing Phase 2 content
2. "Assess" (or "Assess Mode") — existing Phase 3 content
3. "Revive" (or "Revive Mode") — existing Phase 4 content
4. "Reposition" (or "Reposition Mode") — existing Phase 5 content
5. **"History (N)"** — NEW Phase 6 tab, where N = count of findings (hidden if N=0, or always shown per planner discretion)

**History tab badge styling:**
- If any open findings exist: accent color background (`text-accent` or `bg-accent/10`)
- If all findings addressed/invalidated or no findings: gray color
- Badge shows numeric count in small font (e.g., "(5)" or just "5")

**Tab switching behavior:**
- Each tab's content is independent (clicking History tab does not clear mode panel state)
- Mode panels retain "View N prior findings" links in headers (e.g., AssessPanel shows "View 2 prior findings" if 2 open Assess findings exist in history)

---

### HistoryPanel Layout (Full-Width Scrollable Content)

**Header** (sticky, `p-lg`):
1. **Title** — "Engagement history" in `text-heading font-bold`
2. **Filter controls** (horizontal row, flex-wrap to handle narrow sidebar):
   - **Status filter:** Radio buttons or segmented control: "All / Open / Addressed / Invalidated"
   - **Mode filter:** Dropdown or segmented control: "All / Found / Assess / Revive / Reposition"
   - **Date range:** Optional preset buttons "Last 30 days / Last 90 days / All time" (or omit in v1 if space tight)

**Main content area** (scrollable):

**If no findings (empty state):**
```
Heading (text-heading font-bold): "No engagement history yet"
Body (text-body): "Findings appear here after you Found, Assess, Revive, or Reposition a company."
CTA link (text-accent): "Run a mode now"
```

**If findings exist:**
- List of FindingCards grouped by timestamp (newest first per D-10)
- Each FindingCard (see below) separated by `gap-sm` (8px vertical gap)

---

### FindingCard Layout

**Card structure** (padded `p-md`, `bg-card` background, border-bottom or subtle shadow):

1. **Card header row** (flex, justify-between, `gap-md`):
   - Left side:
     - Finding summary text in `text-body font-normal` (1–2 lines max)
     - Below: small `text-label` text showing timestamp relative ("2 days ago")
   - Right side:
     - Mode badge (small colored label: "Found" / "Assess" / "Revive" / "Reposition")
     - Status badge (colored: "open" accent, "addressed" green, "invalidated" muted)

2. **Evidence section** (below summary, `mt-md`):
   - Subheading in `text-label font-normal`: "Evidence:" (optional, omit if only 1 source)
   - List of evidence chips, `gap-xs` between chips
   - Each chip: clickable, navigates to source in Paperclip UI
   - Reuses Phase 3 EvidenceChip component (Issue / Comment / Document / Agent)
   - "See all [N]" expand button if >5 evidence items (reuse Phase 3 pattern)

3. **Status change buttons** (below evidence, `mt-md`, flex row, `gap-xs`):
   - If status = "open":
     - "Mark addressed" button (text style, accent color)
     - "Mark invalidated" button (text style, gray color)
   - If status = "addressed":
     - "Mark invalidated" button only (text style, gray color)
   - If status = "invalidated":
     - "Mark addressed" button only (text style, accent color)
   - Clicking either button opens a confirmation modal (simple: "Are you sure?")
   - On confirm: updates status, shows toast confirmation, re-renders card

---

### Schedules Section (within HistoryPanel or Separate Schedules Tab)

**Section placement:** Planner decides — either below findings in HistoryPanel, or as a separate "Schedules" sub-tab within History. Current spec assumes within HistoryPanel below findings (vertical stacking).

**Section header** (`mt-2xl`, `text-heading font-bold`): "Scheduled check-ins"

**Subheader** (`text-foreground/70`): "These routines automatically trigger Compass modes on a schedule."

**Active routines list:**
- Each routine displayed as a horizontal row, `p-md`, `bg-card` background, `gap-sm` between rows
- Row layout (flex, wrap to mobile if space tight):
  - **Left:** Routine name + mode badge (e.g., "Quarterly vision drift review — Assess")
  - **Center:** Cron expression in human-readable format (e.g., "Every quarter, first Monday at 9am"), `text-label` style
  - **Right (small devices stack vertically):** Last run timestamp in `text-foreground/70` (e.g., "Last run: 2 days ago")
  - **Actions:** Two buttons per routine, right-aligned:
    - "Run check-in now" button (primary, accent style) — triggers routine immediately, shows loading spinner + "Running check-in…" during execution
    - "Disable" button (text style, gray) — disables routine with confirmation modal

**Schedule creation form (collapsible or modal):**
- Triggered by "Create schedule" button above active list (or bottom of list if no active routines)
- Form fields (scrollable if space tight):
  1. **Name input:** Label "Routine name", placeholder "My quarterly audit review", required, max 100 chars
  2. **Mode choice:** Radio buttons "Assess drift review" / "Revive stall diagnosis", required
  3. **Frequency preset:** Radio buttons:
     - "Quarterly drift review" (cron: `0 9 1 1,4,7,10 *`)
     - "Monthly trust-gate review" (cron: `0 9 1 * *`)
     - "Custom cron expression"
  4. **Custom cron input** (shown only if "Custom" selected):
     - Label: "Cron expression (5-field standard)"
     - Placeholder: "0 9 1 1,4,7,10 *"
     - Validation: regex check for `^\d+ \d+ \d+ \d+ \d+$`, shows error if invalid
     - Helper text: "Format: minute hour day month weekday. E.g., '0 9 1 * *' = first of every month at 9am"

- **Form buttons:**
  - "Create schedule" (primary, accent, disabled until all required fields valid)
  - "Cancel" (secondary)

- **Success state:** Form closes, new routine appears in active list, toast shows "Routine '[Name]' created. Next run: [timestamp]"

---

### Mode Panel Integration: "View N Prior Findings" Links

When a mode panel (Found/Assess/Revive/Reposition) has open findings in engagement history:

**Link placement:** In the mode panel header, below the main title or as a small pill badge:
- **Copy:** "View [N] prior findings" (e.g., "View 2 prior findings")
- **Style:** Text link, accent color, underlined
- **Behavior:** Clicking switches to History tab, pre-filters to:
  - Status: "Open" only
  - Mode: current mode (e.g., if clicked from Assess panel, filter by "Assess")
  - Scrolls to top of filtered findings

---

### Assess Mode Context-Refresh Banner

When running Assess drift audit, before displaying drift report:

**Banner placement:** Above DriftReportPanel, sticky, `p-md`, light `bg-card` background, optional left border `border-l-4 border-accent`

**Banner content:**
```
Compared against [N] prior findings still open

[View findings] link → opens History tab pre-filtered
```

**Copy:** "Assessed against [N] findings from prior audits still open. This helps prevent duplicate recommendations." in `text-body` with helper link.

**Behavior:** Drift items are deduplicated: if current audit detects the same drift as a still-open prior finding, the item is marked as "same as prior finding #[id]" with a link.

## Accessibility

- All interactive elements keyboard-navigable (Tab, Enter, Space)
- Status change buttons have `aria-label="Mark as addressed"` or equivalent
- "Run check-in now" button has `aria-label="Run check-in now for [routine name]"`
- Modal backdrops block background interaction (focus trap)
- Evidence chips have `aria-label="Issue #42"` or equivalent per Phase 3 pattern
- Collapsible evidence lists have `aria-expanded="true|false"`
- Filter controls (status/mode/date) have `aria-label` identifying the filter dimension
- Color-coded status badges must have text label fallback (never color-only)
- Finding card timestamp link has `aria-label="Finding from [date]"`
- Error messages linked to form inputs via `aria-describedby` (cron validation error)
- HistoryTabBadge has `aria-label="[N] findings"` for screen readers

## Form Validation Rules

| Check | Validation | Error Message |
|-------|-----------|-----------------|
| Routine name | non-empty, max 100 chars | "Routine name required (max 100 characters)" |
| Mode choice | exactly one selected (Assess or Revive) | "Choose a mode (Assess or Revive)" |
| Frequency preset | exactly one selected (Quarterly, Monthly, or Custom) | "Choose a frequency" |
| Custom cron | (if "Custom" selected) matches `^\d+ \d+ \d+ \d+ \d+$` | "Invalid cron format. Expected 5 fields: minute hour day month weekday" |
| Cron range validation (optional) | Field values within valid ranges (minute 0–59, hour 0–23, day 1–31, month 1–12, weekday 0–6) | "Invalid [field] value. See format help." |

**Finding status change validation:**
- No validation needed (simple state transition, idempotent)

**Routine enable/disable validation:**
- No validation needed (simple state toggle)

## Designer Notes (Claude's Discretion)

This contract locks the **what** (behavior + copy + visual relationships) but leaves **where** for the planner:

1. **Schedules placement** — within HistoryPanel (current rec), separate "Schedules" tab sibling to History, or collapsed section? Recommend within HistoryPanel (cleaner tab structure), but planner may prefer separate tab if schedules grow.

2. **HistoryPanel filter placement** — sticky header (current rec), floating sidebar panel, or collapsible above findings? Recommend sticky (persistent visibility, matches Paperclip UX), but planner may prefer collapsible to save vertical space.

3. **FindingCard evidence max display** — currently 3–5 visible before "See all N". Adjust based on sidebar width during planner phase per Phase 3 precedent.

4. **Cron expression validation** — simple regex (`^\d+ \d+ \d+ \d+ \d+$`) vs full range validation (minute 0–59, etc.). Recommend simple regex + helper text (v1 ship faster), but planner may add full range check for robustness.

5. **Cron-to-English conversion** — library (e.g., cron-parser) vs custom string function (no deps, ~50 LOC). Recommend custom function per D-12 (zero deps, lightweight), but planner may prefer library if complexity grows.

6. **Schedule routine row layout** — single row flex (current) vs stacked card layout (more spacious)? Recommend single row (compact), but planner may stack vertically if space tight.

7. **History tab badge visibility** — always show count, or hide when count=0? Recommend always show (consistent tab visual), but planner may prefer hide-when-empty for cleaner UI.

All above locked in **planner** phase per Phase 1 UI-SPEC.md conventions. UI-SPEC provides the contract; planner places components.
