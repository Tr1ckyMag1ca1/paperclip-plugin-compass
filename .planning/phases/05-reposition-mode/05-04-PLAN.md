**Handler 1: classifyShift** (Data Handler)
- **Purpose:** Classify founder-described strategic shift into affected VISION sections
- **Params:** `{ companyId, description }`
- **Flow:**
  1. Load VISION.md from documents
  2. Parse VISION using parseVision()
  3. Call classifyShift(description, parsedVision) from Wave 1 pure function
  4. Return ShiftScope with affectedSections, confidence, rationale
- **Error:** If VISION not found, return error (reposition requires existing VISION)
- **Return:** `{ success: true, shiftScope: ShiftScope }` or `{ success: false, error: string }`

**Handler 2: generateAmendments** (Action Handler)
- **Purpose:** Generate per-section VISION amendments from scoped interview answers
- **Params:** `{ companyId, interviewAnswers, affectedSections }`
- **Flow:**
  1. Load current VISION from documents
  2. Parse VISION
  3. Call generateAmendments(vision, answers, sections) from Wave 2 orchestrator
  4. Return Amendment[] (scoped, only affected sections)
- **Error:** If quality check fails, return error (founder must retry interview)
- **Return:** `{ success: true, amendments: Amendment[] }` or `{ success: false, error: string }`

**Handler 3: planRepositionCascade** (Action Handler)
- **Purpose:** Plan cascading changes for affected agents
- **Params:** `{ companyId, amendments }`
- **Flow:**
  1. Load VISION (already in context, can pass)
  2. Load all agents
  3. Call planRepositionCascade(vision, amendments, agents) from Wave 2
  4. Return CascadePlan with affectedAgents, customOverrideWarnings, issuesByAgent
- **Error:** If no agents found, return empty CascadePlan
- **Return:** `{ success: true, cascadePlan: CascadePlan }`

**Handler 4: applyRepositionAmendments** (Action Handler)
- **Purpose:** Apply amendments and cascade changes (with approval routing)
- **Params:** `{ companyId, amendments, approvalRouting, repositionRunId }`
- **Flow:**
  1. Call applyRepositionAmendments(ctx, companyId, amendments, routing, runId) from Wave 2
  2. Handle approval routing:
     - founder: apply synchronously, return success result
     - founder+ceo: queue to approvals table, return waiting-approval status
  3. Return ApplyResult with visionDocId, issueIds, wakeupIds, or error
- **Idempotency:** All wakeups use generateRepositionIdempotencyKey(companyId, runId, agentId)
- **Return:** `{ success: true, visionDocId, issueIds, wakeupIds }` or approval-waiting or error

**Helper functions** (optional, if needed for handler orchestration):
- getTitleForShift(confidence): string (for progress bar labels)
- getExplanationForShift(shiftScope): string (for error messages)

**Error handling:**
- VISION not found: return error early (reposition requires existing VISION)
- Parse failure: return error with context
- Quality check failure: return error with missing slots
- Approval rejection: return error waiting-approval, no writes
- Cascade failure: trigger rollback in applyRepositionAmendments, return error + rollback status

**Testing strategy:** Worker handler tests verify:

- generateAmendments produces amendments for affected sections only
- planRepositionCascade screens agents + detects overrides
- applyRepositionAmendments routes founder vs founder+ceo
- All idempotency keys use reposition namespace
- Rollback on failure (cascade failure → cascade issues deleted, VISION reverted)
- Full flow: classifyShift → generateAmendments → planRepositionCascade → applyRepositionAmendments

## Trust Boundaries

| Boundary | Description | Risk |
|----------|-------------|------|
| Handler invocation → orchestrator calls | Worker handlers call backend modules (shift-classify, amend, cascade, apply) | Low — all handlers validate inputs before calling; orchestrators are pure functions with error handling |
| MainPanel routing → RepositionPanel component | Active mode determined by mode detection → component rendering | Low — routing logic simple conditional; component handles null props gracefully |
| Idempotency key generation → wakeup requests | Keys generated for all wakeup requests to prevent duplicates | Low — keys are deterministic (same inputs → same key); no cryptographic requirement (deduplication only) |
| Approval state → apply execution | CEO approval decision read from approvals table before apply | Low — approval routing logic reused from Phase 3 (vetted pattern); only applies if approval.status === "approved" |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-14 | Elevation of Privilege | Handler registration | mitigate | Handlers registered in worker via definePlugin; cannot be called directly by UI; invocation only through Plugin SDK message bridge |
| T-05-15 | Repudiation | Idempotency key format | mitigate | Keys format enforced: compass:reposition:{companyId}:{runId}:{agentId} verified by isValidRepositionIdempotencyKey; malformed keys rejected at wakeup insert |
| T-05-16 | Denial of Service | Handler execution | mitigate | Handlers validate input (VISION exists, amendments non-empty, etc.); long-running operations (cascade, apply) timeout per Paperclip SDK defaults; no unbounded loops |
| T-05-17 | Tampering | Approval state | mitigate | Approval state persisted in approvals table (Paperclip core, immutable audit log); reuses Phase 3 routing logic (no new auth bypass paths introduced) |
